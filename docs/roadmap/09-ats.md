## Phase 9: Shared tables (ATS)

Specified in [`docs/future/13-ats.md` section 13](../future/13-ats.md#13-shared-tables-ats). It needs lightweight tasks on the VM (7h) and starts when a real program needs it, for example an HTTP server with a shared cache or counters. The server measurement (order row 9 of the [roadmap](README.md)) is the natural point to check whether the example server needs one. It lands on the VM in one PR, with the grammar in `docs/grammar/`, the programming skill, the site docs and tests.

- [ ] 9a `Table[K, V]`: `new`, `put`, `put_new`, `get`, `has_key?`, `delete`, `add`, `size`, `keys`, `to_map`; `CHECK-TABLE-VALUE`, `RUNTIME-TABLE-CONTEXT`; `IO.inspect` prints `<Table>` (add it next to `<Task>` in the inspect strings of `docs/vm/02-reference-behavior.md` §2.4); the mutating calls reuse the `concurrency` effect label. `Table` becomes a reserved type and module name. The programming skill must tell `Table` apart from BDD data tables (`BDD.table`). `docs/grammar/06b-builtins.md` gets a `Table` exception to its "Values are immutable" rule (line 9); its effects line ("I/O, tasks, or `test`") already covers `concurrency`, so it stays. Docs: a `site/content/library/data-structures/table.md` page (front matter `title` and `weight`, runnable examples that `tests/site-examples-test.rkt` checks), and a `references/table.md` file in the programming skill plus its row in the skill's "When to read a reference" table (the skill is not published). Add a `CHECK-TABLE-VALUE` check that `V` is not `Void` or `Nil` and that `data-type?` holds for `V`. If phase 9 starts after the freeze of the Racket front end (row 7.2.7), this checker part goes into the Agentica front end ([§35](../future/35-self-hosting.md)), not `src/`; before the freeze, it goes into `src/` as written. `CHECK-MAP-KEY-TYPE` keeps its code for `Table` keys; its message must mention `Table` too. Build the insertion-order layout (§13, Layout) as a persistent ordered map, for example a balanced tree, on the VM. In the BDD docs (`docs/bdd.md`, the programming skill's `references/bdd.md`), say that a table created in `main` is fresh in each scenario, since each scenario is its own VM run after phase 21 (`docs/bdd.md`, "How a run works").
- [ ] 9b Concurrency tests: many tasks calling `Table.add` and `put_new` on one table give the exact total on the VM; no leak in a stress loop that creates and drops many tables; a table created in a step program's `main`, captured by a step block and changed by one scenario, is empty again in the next scenario (over `agentica test`, phase 21).
- [ ] Later, each after a real program needs it: ordered tables, duplicate keys, a block-based `update`, and a bounded or expiring cache as a `std/` module over `Table` (§13, No eviction).

**Done when:** an example with several tasks sharing a cache and a counter runs on the VM with golden output.
