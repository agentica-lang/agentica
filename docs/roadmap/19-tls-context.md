## Phase 19: TLS contexts

Specified in [`docs/future/29-tls-context.md` section 29](../future/29-tls-context.md#29-tls-contexts), decided by the user on 2026-10-12. A new feature, VM-only, after 7i. Order step 7.4: after phase 17 and right after the HTTP streaming items 20e to 20g ([phase 20](20-hybrid-http.md)), before default parameter values (15a, order step 7.5) and `with` (15c, order step 7.6). So every call has a fixed argument list and options live in records; no call needs a default value. Each item is one PR with its own tests and docs.

- [ ] 19a **`TlsContext`, and `TLS` and `HTTP` take it, in one breaking step** (§29.1, §29.2, §29.4 to §29.6). The opaque `TlsContext` (role fixed at creation), the records `TlsClientOptions(ca_file)` and `TlsServerOptions(cert_file, key_file)`, `TLS.client_options()`, `TLS.client_context(options)` and `TLS.server_context(options)` (files read and checked at creation, a key that does not match is an `error`; system trust when `ca_file` is empty, loaded once), `TLS.connect(host, port, context, timeout_ms)` and `TLS.listen(host, port, context)` (SNI and `SSL_set1_host` per connection, as §10.3). A context of the wrong role is the new code `RUNTIME-TLS-CONTEXT-ROLE` at the context argument. In `std/http`: `HttpClientOptions` loses `ca_file`, `HTTP.client(options, tls)`, `HTTP.listen_tls(host, port, tls, handler, options)` and `HTTP.listen_stream_tls(host, port, tls, handler, options)`; `HttpWire.client` takes the context and drops its own `SSL_CTX`. The file-path forms are removed (one way), with hints in `grammar.md` §7; `TlsContext`, `TlsClientOptions` and `TlsServerOptions` become reserved names. VM: a GC object over a `malloc`'d `SSL_CTX` record, freed by a Boehm finalizer run on demand between turns (`GC_set_finalize_on_demand`, `GC_invoke_finalizers` at the scheduler's safe point) and by the end of the run (a `malloc`'d list), a stated exception in `docs/vm/05-values-execution-builtins.md` §5.3; `RUNTIME-INTERNAL` under the fuzzer's `no_files`; context creation is a thread-pool job. Migrate every TLS and HTTPS program, fixture and test (`tls-*` and `http-*` golden fixtures, `tests/vm-tls-test.rkt`, `tests/vm-http-test.rkt`, examples, the site, the skill). Tests: the golden fixtures, Python `ssl` peers, the C test of a dropped context with a live socket, and the checker hints of §29.8. Docs: `docs/grammar.md`, `references/network.md` and `references/diagnostics.md`, `site/content/library/network.md`, `docs/vm/10-io-tls-processes-http.md` §10.3, `docs/vm/05-values-execution-builtins.md` §5.3, the development skill (`references/vm.md`), and one CHANGELOG entry under "Changed" (§29.5).
- [ ] 19b **`TLS.upgrade` (STARTTLS)** (§29.3): `TLS.upgrade(socket, context, host, timeout_ms) -> Result[Socket]` over an open TCP socket; the role comes from the context (a server context needs `host == ""`, else `RUNTIME-TLS-CONTEXT-ROLE`); the plain socket is closed for the program on success and failure; unread input before the handshake, or a TLS socket, is an `error`. Tests: a golden fixture with both sides in one program, and Python peers for each side in `tests/vm-tls-test.rkt`. Docs: `docs/grammar.md`, `references/network.md`, `site/content/library/network.md`, `docs/vm/10-io-tls-processes-http.md` §10.3, CHANGELOG ("Added").
- Not in this phase: the later options of §29.7 (`min_version`, ALPN, client certificates, `ca_data`, peer certificate info), each its own item after `with` (15c), so adding a field does not break the canonical `TLS.client_options().with(...)` form. Never: a verify-off path, cipher or curve strings, `openssl.cnf` settings, versions below TLS 1.2.

**Done when:** a program builds one client context and one server context at start-up and shares them across many connections and tasks; `TLS`, `HTTP.client` and `HTTP.listen_tls` take only contexts; a STARTTLS exchange works against Python on both sides; and no repository program uses a TLS file path outside the options records.
