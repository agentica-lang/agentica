## Phase 18: VM metrics

Specified in [`docs/future/28-vm-metrics.md` section 28](../future/28-vm-metrics.md#28-vm-metrics). Three small PRs, on the VM only, in order step 7.5: a new VM-only feature after 7i, before the server measurement (7j), which reads its GC and run-queue numbers. No grammar change and no builtin: it is a tool of `agentica-vm`, like VM tracing (14a). The endpoint does not use the HTTP stack, so it does not wait for anything but 7i. Every metric is derived at scrape time from state the VM already keeps, or comes from an enabled-only hook at an existing trace point that starts at the first scrape; with metrics off the cost is zero, and `make vm METRICS=0` compiles them out (§28.2).

- [ ] 18a Metrics from the VM's own state, written to a file (`docs/future/28-vm-metrics.md` §28.3 to §28.5): `vm/metrics.h` and `vm/metrics.c`; the observe word shared with the trace points; the metrics thread and the snapshot the scheduler fills on request (unref'd async handle, no steps, no turn cost); the Prometheus text format 0.0.4; the derived and existing-counter metrics (build info, `process_*` from `/proc`, GC, tasks, steps, open resources, end of run); `AGENTICA_VM_METRICS_FILE` (a `.prom` path, atomic rewrite every 15 seconds and at the end, the trace file's owner and symlink rules); `Process.spawn` removes the variables from a child's environment; `make vm METRICS=0` (built in the `vm-sanitizers` job) and `metrics off` in `--version`; the Makefile and the test runners remove the variables. Tests: C tests of the renderer and the path checks, an independent Python parser of the format, known numbers from fixtures, golden fixtures unchanged with metrics on, a reader that always finds a whole file. Docs: `docs/vm/` and the development skill.
- [ ] 18b The endpoint (§28.5): `AGENTICA_VM_METRICS=[IP:]PORT` (a bare port binds `127.0.0.1`; port 0 for tests, reported by the `metrics listen` trace line), `GET /metrics` only, with 404, 405, 400, 431 and 503, `Connection: close`, 8 KiB, 5 seconds and 4 connections; the listener lives on the metrics thread's own loop, so it never keeps the VM alive. Tests: replies from a Python client, the VM ends while a client is connected, golden fixtures unchanged while scraped every 100 ms, and the first overhead numbers in `docs/vm-benchmarks.md` (§28.8).
- [ ] 18c Enabled-only hooks (§28.3, §28.4): turns by end, turn-cost units, the run-queue delay histogram, I/O jobs by kind and result, I/O bytes, processes, TCP connections and errors, and the GC pause total (`GC_start_performance_measurement`); each at an existing trace point and sharing its test; started at the first snapshot request (at start-up in file mode). Tests: known counts from fixtures; the overhead check (`benchmarks/run.py --metrics-overhead` on `calls` and `knight-tour`: off, on with no scraper, on with a scraper every second; about 0, about 0, below 2%), recorded in `docs/vm-benchmarks.md`.

To evaluate later, not in this phase: a GC pause histogram (needs a documented exception to the no-globals rule) and metrics defined by programs (after shared tables, phase 9, and HTTP on the VM; a `std/metrics` renderer, never a builtin, §28.6).

**Done when:** a Prometheus server scrapes a running Agentica server on the VM and Grafana graphs its GC, tasks, run-queue delay and I/O; a cron script leaves its exit code and totals in a `.prom` file; and the golden fixtures give the same output with metrics on.
