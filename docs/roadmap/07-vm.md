## Phase 7: Bytecode VM

Replace the tree-walking evaluator with a bytecode VM written in C with the Boehm GC, step by step, without changing the language. The Racket front end (lexer, parser, module linker, checker) stays. It lowers the checked program to a typed intermediate form (IR), then to bytecode that the VM runs.

Why a VM and not a transpiler or LLVM IR: agents write, run and repair in a loop, so start-up time matters more than peak speed, and users should not need a compiler toolchain. A VM keeps `--max-steps`, the call-depth limit and located runtime diagnostics almost for free. Transpiling to C can come later from the same IR if native binaries are needed. Why C with Boehm: C is small, fast to build and available everywhere, and the VM can ship as one binary (OpenSSL is vendored and linked statically, `docs/vm/10-dependencies-and-platforms.md` 10.0). The Boehm GC removes manual memory management from the VM and runtime, so values can be shared freely without reference counting. The cost is that the runtime (tasks, files, processes, TLS, HTTP, JSON) must be written in C, so memory safety depends on discipline and tooling (sanitizers, fuzzing of the loader).

Rules for every subphase:

- The language does not change. `grammar.md` stays the contract. The VM is the only backend and the reference; 7i deleted the Racket evaluator.
- Catch-up work is tested with golden outputs (`tests/fixtures/vm/<name>.expected`, rewritten by `make goldens` with a reviewed diff) and independent Node/Python peers, not against the evaluator (`docs/vm/README.md` §1). A runaway program stops with `RUNTIME-STEP-LIMIT` under `--max-steps`. VM messages must be clear for agents, which evaluation rounds judge.
- New features are VM-only.
- The compiler may optimize freely as long as the exit code, stdout, program stderr and diagnostic codes in the goldens stay the same: inlining, constant folding, common subexpression elimination, loop-invariant code motion, and merging or moving `STEP`s (a runaway loop must still hit `RUNTIME-STEP-LIMIT`; step counts may change).
- Diagnostic codes stay stable. The VM reports `RUNTIME-` diagnostics with the original source span.
- No placeholder files, directories or opcodes for later subphases.
- C naming: every exported function, type and global of the VM library uses the `agc_` prefix (`agc_value`, `agc_vm_run`); macros and enum constants use `AGC_` (`AGC_OP_ADD`). File-local helpers are `static`, so they need no prefix.

### 7a: Baseline measurements (merged into 7g)

The Racket evaluator stayed in the repository until 7i, so it could be measured at any time. Profiling a Racket tree walker does not inform the design of a C VM. All measurement work therefore happens in 7g, when both backends run the same programs.

### 7b: Design decisions (`docs/vm/`)

- [x] IR: closures (block bodies with their captured values): each block is its own IR function; free variables are captured by value; `&name` is a closure with no captures.
- [x] IR: shape of the lowered program: flat instruction lists over numbered slots, labels, typed operations, spans; the checker records expression types for the lowerer.
- [x] Bytecode: register machine, 46 opcodes, generic `CALL_BUILTIN`, constant pool, type/struct/enum/function tables, span table, format version.
- [x] Serialization between Racket and the VM: little-endian binary with magic `AGCB`, format version and Agentica version, rejected on mismatch.
- [x] Value representation in C: 16-byte tagged values with the Boehm GC; HAMT maps with insertion order; checked accessors for every value read.
- [x] Execution limits: one step per former AST entry through `STEP` instructions; counts and spans matched the evaluator at first, and now only the `RUNTIME-STEP-LIMIT` outcome must hold.
- [x] Call-depth limit (10000) and stack layout: growing register and frame arrays per task; resumable native frames for the higher-order `List` builtins.
- [x] How the CLI runs the VM: `dist/agentica-vm` from 7e; `agentica --vm` in 7i; the release ships both binaries.
- [x] Dependency policy: C11, dynamic libc; libgc vendored as a pinned git submodule (`vm/third_party/bdwgc`, v8.2.12) and linked statically (with `AGENTICA_GC=vendored` and in the release; a default Linux build now links the system libgc); libuv for the event loop (also a pinned submodule, added in 7h); OpenSSL 3.5 LTS for TLS (7h), vendored as a pinned git submodule (`vm/third_party/openssl`) and built static in dev, CI and release (user decision of 2026-10-12, which replaced the first plan of a dynamic system OpenSSL) (`docs/vm/10-dependencies-and-platforms.md` 10.0, with the license rule for vendored code); HTTP start lines and headers parsed by picohttpparser (MIT, a pinned submodule `vm/third_party/picohttpparser`, added in 7h) behind our own adapter, with HTTP framing, limits and validation and the JSON encoder written in C; JSON parsing on the yyjson reader (MIT, a pinned submodule `vm/third_party/yyjson`, added with the JSON PR). Linux, macOS and Windows (MSYS2 UCRT64).
- [x] Seeded `Random`: the VM has its own generator (xoshiro256**), so seeded sequences repeat per backend and differ between backends by design (`docs/vm/05-values-execution-builtins.md` §7.4).
- [x] Build and CI: `make vm` with `-Werror` and hardening flags, `make vm-test`, a sanitizer job (ASan, UBSan), a GC stress run, a loader fuzz run, and Linux, macOS and Windows jobs.

**Done when:** `docs/vm/` answers each item above and the open decisions are closed.
