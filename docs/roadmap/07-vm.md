## Phase 7: Bytecode VM

Run the programs on a bytecode VM written in C with the Boehm GC, step by step,
without changing the language. The front end (lexer, parser, module linker,
checker, in `compiler/`) lowers the checked program to a typed intermediate form
(IR), then to bytecode that the VM runs.

Why a VM and not a transpiler or LLVM IR: agents write, run and repair in a
loop, so start-up time matters more than peak speed, and users should not need a
compiler toolchain. A VM keeps `--max-steps`, the call-depth limit and located
runtime diagnostics almost for free. Transpiling to C can come later from the
same IR if native binaries are needed. Why C with Boehm: C is small, fast to
build and available everywhere, and the VM can ship as one binary (OpenSSL is
vendored and linked statically, `docs/vm/10-dependencies-and-platforms.md`
10.0). The Boehm GC removes manual memory management from the VM and runtime, so
values can be shared freely without reference counting. The cost is that the
runtime (tasks, files, processes, TLS, HTTP, JSON) must be written in C, so
memory safety depends on discipline and tooling (sanitizers, fuzzing of the
loader).

Rules for every subphase:

- The language does not change. `grammar.md` stays the contract. The VM is the
  only backend and the reference.
- Catch-up work is tested with golden outputs
  (`tests/fixtures/vm/<name>.expected`, rewritten by `make goldens` with a
  reviewed diff) and independent Node/Python peers
  (`docs/vm/README.md` §1). A runaway program stops with `RUNTIME-STEP-LIMIT`
  under `--max-steps`. VM messages must be clear for agents, which evaluation
  rounds judge.
- New features are VM-only.
- The compiler may optimize freely as long as the exit code, stdout, program
  stderr and diagnostic codes in the goldens stay the same: inlining, constant
  folding, common subexpression elimination, loop-invariant code motion, and
  merging or moving `STEP`s (a runaway loop must still hit `RUNTIME-STEP-LIMIT`;
  step counts may change).
- Diagnostic codes stay stable. The VM reports `RUNTIME-` diagnostics with the
  original source span.
- No placeholder files, directories or opcodes for later subphases.
- C naming: every exported function, type and global of the VM library uses the
  `agc_` prefix (`agc_value`, `agc_vm_run`); macros and enum constants use
  `AGC_` (`AGC_OP_ADD`). File-local helpers are `static`, so they need no
  prefix.

### 7h: Runtime services on the VM

§10.7), BDD in Agentica ([phase 21](21-bdd-in-agentica.md)) and the
architecture note ([§16](../vm/16-architecture.md#16-vm-architecture)).

Multicore schedulers (`docs/vm/16-architecture.md` §16.9, rules per thread in
`docs/vm/10-io-multicore.md` §10.2.3) are built: N scheduler threads and the I/O
thread, `--schedulers N` defaulting to the number of cores. Test decisions that
stay: TSan builds have no GC (TSan does not get along with Boehm's
stop-the-world), so the GC-threaded build is covered by a GC-stress run with
`--schedulers 4`; with N=1 the black-box parity rule stays, and the golden,
seeded and `--max-steps` tests run with `--schedulers 1`; site examples, smoke
tests and BDD runs that use tasks run with `--schedulers 1` or must not depend
on cross-task order. TLS crypto stays on the I/O thread unless measurements ask
(§16.10).

### 7m: JIT

- [ ] A baseline JIT, required and not gated
  ([§6.4](../vm/05-values-execution-builtins.md#64-jit); what is left:
  [#756](https://github.com/agentica-lang/agentica/issues/756)). After the VM
  layers (7l) and the server measurement (7j), so it has numbers to beat (order
  step 9.1); independent of 7i and of the multicore decision. Hot functions run
  as native code with the same results as the interpreter. Done: the x86-64
  emitter (`--jit`, on by default): Int and Float arithmetic, compares, jumps,
  `STEP`, list, field, enum and Result reads, string joins (`CONCAT`) and text
  forms (`TO_TEXT`); other instructions run in the interpreter between two runs
  of compiled code. A CALL of a compiled function is a native call in compiled
  code, which also calls the builtins whose row is marked `direct` (String,
  List, Map and Set operations) itself; other non-leaf builtins leave for the
  interpreter. The arm64 emitter is deferred beyond 0.10.0.
