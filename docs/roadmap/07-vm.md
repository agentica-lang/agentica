## Phase 7: Bytecode VM

Run the programs on a bytecode VM written in C with the Boehm GC, without
changing the language. The front end in `compiler/` lowers the checked program
to a typed intermediate form (IR), then to bytecode that the VM runs.

Why a VM and not a transpiler or LLVM IR: agents write, run and repair in a
loop, so start-up time matters more than peak speed, and users should not need a
compiler toolchain. A VM keeps `--max-steps`, the call-depth limit and located
runtime diagnostics almost for free. Why C with Boehm: C is small, fast to build
and available everywhere, and the VM ships as one binary
(`docs/vm/10-dependencies-and-platforms.md` 10.0). Boehm removes manual memory
management, so values are shared freely without reference counting. The cost is
that the runtime must be written in C, so memory safety depends on discipline
and tooling (sanitizers, fuzzing of the loader).

Rules for every subphase:

- The language does not change. `grammar.md` stays the contract. The VM is the
  only backend and the reference.
- Work is tested with golden outputs and independent Node/Python peers; the
  golden contract and the optimization freedom it leaves are in
  `docs/vm/README.md` §1. VM messages must be clear for agents, which evaluation
  rounds judge.
- New features are VM-only.
- Diagnostic codes stay stable. The VM reports `RUNTIME-` diagnostics with the
  original source span.
- No placeholder files, directories or opcodes for later subphases.
- C naming: every exported function, type and global of the VM library uses the
  `agc_` prefix (`agc_value`, `agc_vm_run`); macros and enum constants use
  `AGC_` (`AGC_OP_ADD`). File-local helpers are `static`, so they need no
  prefix.

examples, smoke tests and BDD runs that use tasks run with `--schedulers 1` or
must not depend on cross-task order. TLS crypto stays on the I/O thread unless
measurements ask (§16.10).
