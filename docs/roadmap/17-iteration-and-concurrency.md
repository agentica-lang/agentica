## Phase 17: Iteration and concurrent collections

Specified in [`docs/future/27-iteration-and-concurrency.md` section 27](../future/27-iteration-and-concurrency.md#27-iteration-and-concurrent-collections), with the one-way principle of §25, its table of one form for each job, and its rule that the concurrency primitives are C builtins and higher-level helpers are Agentica code in the compiler prelude. All items come after 7i (order 7.2) and are VM-only. 17a and 17b are order step 7.3, the first new features after 7i, before HTTP streaming, which is built on channels, and `TlsContext` (order step 7.4), and before default parameter values (15a) and the other items of order steps 7.5 and 7.6. 17a adds the general checker rule for builtins whose block result is `Result[T]` (`try` works in the block even when `T` is inferred, §25.9); 15i reuses it for `File.open`. They land before strict diagnostics (phase 16), so their examples, golden fixtures, tests and site pages are written in today's forms, and each phase 16 PR counts and migrates them (§26, "Impact on existing code"). They need neither faster lists (8d) nor the prelude: both are C builtins, under the library rule's exception 1 (time) for 17a and exception 4 (its own memory layout) for 17b, and both park tasks, which only the scheduler can do (§27.1 and §27.2, "Where it lives"). 17c is order step 8.2: prelude code over channels, after 17b and after the prelude (15f) and lambdas (15e). One PR per item, in the order 17a, 17b, 17c, each with `grammar.md`, the programming skill (`references/tasks.md`), the site pages, the development skill's notes, the `docs/vm/` sections named in §27, and tests that assert codes and spans (checker tests, golden VM fixtures, site examples, and hermetic I/O tests against a Python counterpart on port 0). Section 27.4 (lazy streams) adds no item: it is to evaluate later, with its criteria. Section 27.5 adds no item: its help hints come with 17a and 17b.

- [ ] 17a `Task.map(items, limit, timeout_ms) do |x| ... end` (§27.1): bounded concurrency (`limit` 1 to 1024, `RUNTIME-INVALID-COUNT`), a per-item timeout (`RUNTIME-INVALID-DURATION` when not positive), one `Result` per item in input order, the block's `error` does not stop the others, and a timed-out item and its descendant tasks are cancelled (items are children of the caller; when a task ends, its running children move to its parent; a cancelled caller's group is marked dead, so its pending items never start). Arguments are checked before the empty-list shortcut. Checker: the general rule for builtins whose block result is `Result[T]`, added here (§27.1, §25.9): `try` works in the block even when `R` is inferred, since the outer type is always `Result`; 15i reuses it for the `File.open` block. A timed-out item leaks the handles it opened until the run ends; a connection that an HTTP request leases internally is closed when its detached job ends. VM: the builtin and its group object, and task cancellation (`agc_task_cancel`, parent and children links on each task; the core, for ready tasks, I/O jobs, lock waits, awaits, sleeps and HTTP pool waits, lands earlier in 20b for `HTTP.close_server`, [phase 20](20-hybrid-http.md), with its C tests in `vm/tests/task_cancel_test.c`; 17a adds only the `Task.map` group and caller states and their C test): a cancelled task's I/O job is detached (it ends on its own deadline, its result is dropped, the handle is not closed), the task leaves lock and await queues, a handle lock's `next_owner` passes to the next waiter, and tasks parked in `Task.await` on it are woken and halt with `RUNTIME-TASK-CANCELLED` at their own span; a task parked as a `Task.map` caller or on a `Task.sleep` timer is cancelled too. That VM path and its C test come earlier, with the cancellation core of 20b; a program cannot reach it before channels. Appended builtin, no format bump. Hints for `Task.async_stream`, `Task.async`, `Parallel.map` and `Thread.new`. Tests: the checker tests, golden fixtures and C tests of §27.1, `tests/vm-task-map-test.rkt`, planned like `tests/vm-latency-test.rkt` (in `test-omit-paths` of `tests/info.rkt`, its own `make vm-task-map` target, a CI step in the `test` job after `make vm-latency`, a line in the Commands section of `AGENTS.md`), which holds every timing-dependent case of phase 17, since golden fixtures record step counts and run the `--max-steps` sweep and must not depend on timing (concurrency bound, timing with safe bounds, timeout, cancellation of a grandchild whose parent ended and of a nested `Task.map` with `limit` 1 whose pending items never print, and a detached read on a TCP socket shared by two items, against a Python peer on port 0) and the Python `http.server.ThreadingHTTPServer` counterpart (with a timed-out request that leaves no open socket). Docs: `grammar.md` ("Lightweight tasks", §7 hints), `references/tasks.md` (the `limit` sentence and the handle rules of §27.1), `site/content/library/task.md` and `site/content/tour/tasks.md`, `docs/vm/10-io-scheduler.md` §10.2.1 and §10.2.2, `docs/vm/10-io-multicore.md` §10.2.3.
- [ ] 17b `Channel[T]` (§27.2): `Channel.new(capacity)`, `send(value, timeout_ms) -> Result[Void]`, `recv(timeout_ms) -> Result[T]`, `close`, `closed?` (closed, buffer empty, no reservation outstanding); bounded only (capacity 1 to 1,048,576), FIFO, required timeouts (0 means do not wait), waiters served in order with a reserved hand-off, no lost values under cancellation, and `close` revokes the slot reservations of senders that have not run yet; a `recv` on a closed channel waits while a reservation is outstanding. The producer closes on every path (`result = send_all(jobs)`, `jobs.close`, `return result`), since a receive loop whose producer never closes polls forever. New codes: `CHECK-EXPECTED-TYPE` for `Channel.new` without an expected type, and `RUNTIME-TASK-AWAIT-CYCLE`: `Task.await` follows the target's await chain and halts on a cycle, which channels make possible (§27.1, "Await cycles"). Breaking change: `Channel` becomes a reserved name (`CHECK-REDEFINED-NAME`; say so in the changelog). VM: `vm/channel.c` (ring buffer, wait FIFOs with reservations, park with retry on a timer-only job, as the handle lock does); cancelled waiters hand their reservation on; appended builtins, no format bump. Hints for `Enumerator.new`, `Fiber.new`, `xs.lazy`, `Agent`, `Mutex.new` and `SizedQueue.new` (§27.5). Tests: the checker tests, golden fixtures and C tests of §27.2, including the await-cycle fixtures, the two `RUNTIME-TASK-CANCELLED` cases moved from 17a, in `tests/vm-task-map-test.rkt` (an await made after the cancel, and one already parked when the item times out), the hand-off case in `tests/vm-task-map-test.rkt` (a woken receiver is cancelled and the next one is still served), the C tests of the two late-reservation races with `close`, and, in `tests/vm-task-map-test.rkt`, a socket handed to a worker against a Python TCP counterpart on port 0. Docs: `grammar.md` (channels, reserved names, §7 hints), `references/tasks.md` (the canonical receive loop, pipeline, fan-in (a coordinator awaits all sources, then closes) and owner-task patterns, and the close-on-every-path rule) and `references/diagnostics.md` (`CHECK-EXPECTED-TYPE`, `RUNTIME-TASK-AWAIT-CYCLE`, `RUNTIME-TASK-CANCELLED` on the VM), the site's task pages (or a new `site/content/library/channel.md`), `docs/vm/10-io-scheduler.md` §10.2.1 (stall check, await-cycle check) and §10.2.2, `docs/vm/10-io-multicore.md` §10.2.3; `docs/future/08-concurrency.md` then keeps only its open questions.
- [ ] 17c Order step 8.2, after 15f and 17b. `Task.await(task, timeout_ms) -> Result[T]` (§27.3), written in the compiler prelude (`stdlib/prelude/task.agc`): a helper task waits for the target and signals a capacity-1 `Channel[Nil]`; the caller receives with the timeout and returns the target's cached result. A timeout gives `error("task: timed out")` and does not cancel the task; a later `Task.await` on it is valid; a settled task never times out (checked before and after the wait); `timeout_ms` must be positive (`RUNTIME-INVALID-DURATION` through `__fail_arg`); a cancelled target halts at the user's call while the caller waits, and a helper whose caller already timed out ends quietly. What it adds to the prelude mechanism: one catalog name with a C body for arity 1 and a prelude body for arity 2; a second body for `Task[Void]` (the last line differs); lambdas in prelude files carry the prelude flag; a task spawned with a prelude-flagged entry stores the user's spawning call span, which the span rule uses when the task has no user frame (§25.6's crafted-`.agcb` sentence is updated in this PR); a task whose entry has the prelude flag is a helper and does not count as pending for `RUNTIME-BDD-PENDING-TASKS`; and two prelude-only builtins, `__task_settled?` and `__task_wait`, guarded like `__fail_arg` and appended to the builtin table (no format bump). Tests: the golden fixtures, checker tests and loader test of §27.3, and in `tests/vm-task-map-test.rkt` its timing-dependent cases, with a step limit inside the helper reported at the user's call. Docs: `grammar.md` ("Lightweight tasks"), `references/tasks.md`, `site/content/library/task.md`, the development skill's notes, `docs/vm/03-ir-and-bytecode.md` §4.5.
- Not in this phase: lazy streams (§27.4, to evaluate later), a public `Task.cancel` (open in §8), `select` over several channels (§27.2, "Left out"), and other prelude helpers such as "the first of several tasks" or "all settled" (each needs its own spec, §27). CPU speed-ups from `Task.map` come only with the multicore schedulers (7h item, gated at order step 11); a CPU-bound `Task.map` program joins round 2 of the benchmarks (phase 12) as evidence for that decision.

**Done when:** the site examples of all three items run on the VM; the `http.server` test shows `Task.map` running 8 delayed requests in about the time of one, and a timed-out HTTP item leaves no open socket; a timed-out item leaves no task running and closes no shared handle; a producer, workers and collector pipeline runs with fixed output; an await cycle halts with `RUNTIME-TASK-AWAIT-CYCLE`; a timed `Task.await` returns its timeout and the task's result is still there for the next await; and an evaluation round shows agents pick `Task.map` for list fan-out and channels for pipelines, with the hints of §27.5 leading them away from generators, `Agent` and locks.
