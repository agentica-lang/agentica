## Phase 17: Iteration and concurrent collections

Specified in [`docs/future/27-iteration-and-concurrency.md` section 27](../future/27-iteration-and-concurrency.md#27-iteration-and-concurrent-collections), with the one-way principle of §25, its table of one form for each job, and its rule that the concurrency primitives are C builtins and higher-level helpers are Agentica code in the compiler prelude. All items come after 7i (order 7.2) and are VM-only. 17a and 17b are order step 7.5, after the items of order step 7.4, because 17a uses the checker rule of 15i (`try` in a block whose result is `Result[T]`, §25.9). They need neither faster lists (8d) nor the prelude: both are C builtins, under the library rule's exception 1 (time) for 17a and exception 4 (its own memory layout) for 17b, and both park tasks, which only the scheduler can do (§27.1 and §27.2, "Where it lives"). 17c is order step 8.2: prelude code over channels, after 17b and after the prelude (15f) and lambdas (15e). One PR per item, in the order 17a, 17b, 17c, each with `grammar.md`, the programming skill (`references/tasks.md`), the site pages, the development skill's notes, the `docs/vm/` sections named in §27, and tests that assert codes and spans (checker tests, golden VM fixtures, site examples, and hermetic I/O tests against a Python counterpart on port 0). Section 27.4 (lazy streams) adds no item: it is to evaluate later, with its criteria. Section 27.5 adds no item: its help hints come with 17a and 17b.

- [ ] 17a `Task.map(items, limit, timeout_ms) do |x| ... end` (§27.1): bounded concurrency (`limit` 1 to 1024, `RUNTIME-INVALID-COUNT`), a per-item timeout (`RUNTIME-INVALID-DURATION` when not positive), one `Result` per item in input order, the block's `error` does not stop the others, and a timed-out item and its descendant tasks are cancelled. VM: the builtin and its group object, and task cancellation (`agc_task_cancel`, parent and children links on each task): a cancelled task's I/O job is detached (it ends on its own deadline, its result is dropped, the handle is not closed), the task leaves lock and await queues, and a handle lock's `next_owner` passes to the next waiter. The VM path for `Task.await` on a cancelled task (`RUNTIME-TASK-CANCELLED`) comes here with a C test only, since a program cannot reach it before channels. Appended builtin, no format bump. Hints for `Task.async_stream`, `Task.async`, `Parallel.map` and `Thread.new`. Tests: the checker tests, golden fixtures and C tests of §27.1, `tests/vm-task-map-test.rkt` (concurrency bound, timing with safe bounds, timeout, cancellation and a detached read on a shared handle) and the Python `http.server` counterpart. Docs: `grammar.md` ("Lightweight tasks", §7 hints), `references/tasks.md` (the `limit` sentence and the handle rules of §27.1), `site/content/library/task.md` and `site/content/tour/tasks.md`, `docs/vm/10-io-scheduler.md` §10.2.1 and §10.2.2, `docs/vm/10-io-multicore.md` §10.2.3.
- [ ] 17b `Channel[T]` (§27.2): `Channel.new(capacity)`, `send(value, timeout_ms) -> Result[Void]`, `recv(timeout_ms) -> Result[T]`, `close`, `closed?` (closed and drained); bounded only (capacity 1 to 1,048,576), FIFO, required timeouts (0 means do not wait), waiters served in order with a reserved hand-off, no lost values under cancellation. New codes: `CHECK-EXPECTED-TYPE` for `Channel.new` without an expected type, and `RUNTIME-TASK-AWAIT-CYCLE`: `Task.await` follows the target's await chain and halts on a cycle, which channels make possible (§27.1, "Await cycles"). Breaking change: `Channel` becomes a reserved name (`CHECK-REDEFINED-NAME`; say so in the changelog). VM: `vm/channel.c` (ring buffer, wait FIFOs with reservations, park with retry on a timer-only job, as the handle lock does); cancelled waiters hand their reservation on; appended builtins, no format bump. Hints for `Enumerator.new`, `Fiber.new`, `xs.lazy`, `Agent`, `Mutex.new` and `SizedQueue.new` (§27.5). Tests: the checker tests, golden fixtures and C tests of §27.2, including the await-cycle fixtures, the `RUNTIME-TASK-CANCELLED` fixture moved from 17a, the hand-off fixture (a woken receiver is cancelled and the next one is still served), and a socket handed to a worker against a Python TCP counterpart on port 0. Docs: `grammar.md` (channels, reserved names, §7 hints), `references/tasks.md` (the canonical receive loop, pipeline, fan-in and owner-task patterns) and `references/diagnostics.md` (`CHECK-EXPECTED-TYPE`, `RUNTIME-TASK-AWAIT-CYCLE`, `RUNTIME-TASK-CANCELLED` on the VM), the site's task pages (or a new `site/content/library/channel.md`), `docs/vm/10-io-scheduler.md` §10.2.1 (stall check, await-cycle check) and §10.2.2, `docs/vm/10-io-multicore.md` §10.2.3; `docs/future/08-concurrency.md` then keeps only its open questions.
- [ ] 17c Order step 8.2, after 15f and 17b. `Task.await(task, timeout_ms) -> Result[T]` (§27.3): a second arity of `Task.await`, written in the compiler prelude (`stdlib/prelude/task.agc`) over a capacity-1 channel and a helper task; a timeout gives `error("task: timed out")` and does not cancel the task; a later `Task.await` on it is valid; `timeout_ms` must be positive (`RUNTIME-INVALID-DURATION` through `__fail_arg`); a second body for `Task[Void]` with a `Channel[Nil]`. VM: one addition to the prelude span rule (a task spawned from a prelude frame reports at the user's call). Tests: the golden fixtures, checker test and VM test of §27.3. Docs: `grammar.md` ("Lightweight tasks"), `references/tasks.md`, `site/content/library/task.md`, the development skill's notes.
- Not in this phase: lazy streams (§27.4, to evaluate later), a public `Task.cancel` (open in §8), `select` over several channels (§27.2, "Left out"), and other prelude helpers such as "the first of several tasks" or "all settled" (each needs its own spec, §27). CPU speed-ups from `Task.map` come only with the multicore schedulers (7h item, gated at order step 11); a CPU-bound `Task.map` program joins round 2 of the benchmarks (phase 12) as evidence for that decision.

**Done when:** the site examples of all three items run on the VM; the `http.server` test shows `Task.map` running 8 delayed requests in about the time of one; a timed-out item leaves no task running and closes no shared handle; a producer, workers and collector pipeline runs with fixed output; an await cycle halts with `RUNTIME-TASK-AWAIT-CYCLE`; a timed `Task.await` returns its timeout and the task's result is still there for the next await; and an evaluation round shows agents pick `Task.map` for list fan-out and channels for pipelines, with the hints of §27.5 leading them away from generators, `Agent` and locks.
