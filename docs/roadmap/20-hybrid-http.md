## Phase 20: HTTP on the VM (simple, synchronous, hybrid)

Specified in [`docs/future/30-hybrid-http.md` section 30](../future/30-hybrid-http.md#30-http-on-the-vm-simple-synchronous-hybrid), decided by the user on 2026-10-12. Two parts:

- **20a to 20d, simple HTTP**, are the HTTP catch-up of order step 7.1: after TLS on the VM (today's API, roadmap 7h) and before BDD in Agentica (phase 21, planned by its own docs PR), then 7i. They replace roadmap 7h's C-only HTTP item ([`07-vm.md`](07-vm.md)). Whole requests and whole responses, `String` bodies (strict UTF-8, `max_body_bytes` 1 MiB by default, up to 64 MiB), handlers that return `Result[HttpResponse]`, responses always sent with `Content-Length`, and no streaming. C keeps head parsing, whole-body framing and limits, the connection pool and the server's task group (the `HttpWire` builtins); Agentica (`std/http.agc`, imported as `HTTP`) keeps the rest. 20d is a breaking change made during the catch-up (§30.8).
- **20e to 20g, streaming**, are new features at order step 7.4, VM-only: after phase 17 (`Task.map` and channels), since they are built on `Channel[T]` (17b), and right before `TlsContext` (phase 19). Their calls have fixed argument lists, so default parameter values (15a, order step 7.5) never change them.

Each item is one PR that keeps its own tests and docs (the stacked-PR rule), lists the docs it updates, and ticks itself here. Simple HTTP keeps today's TLS parameters (`ca_file`, `cert_file`, `key_file`) until phase 19 changes `TLS` and `HTTP` together.

- [ ] 20a **Wire layer, server side** (§30.5, §30.9). Vendor picohttpparser as the git submodule `vm/third_party/picohttpparser`, pinned to v1.4 and built by the Makefile like yyjson at the baseline (`docs/vm/10-dependencies-and-platforms.md` §10); the adapter `vm/http_parse.h` and `vm/http_pico.c` with every check of `docs/vm/10-io-tls-processes-http.md` §10.6 (the pre-scan, the start-line check, the target, method, obs-fold, `Host`, framing and smuggling rules); the body decoder `vm/http_body.c` (`Content-Length` and chunked, saturating sizes, trailers checked and dropped) filling one `malloc`'d buffer within `max_body_bytes`; the new builtin records `HttpRequest` and `HttpResponse` (body `String`); `HttpWire.read_request` (100 Continue, 417, 501 for `CONNECT` and `Upgrade`, 413, 431, 505, 400 for a non-UTF-8 body, and the error answer written in C before the socket closes) and `HttpWire.write_response` (`Content-Length` always, `HEAD`, 204 and 304, header validation). From this PR on, a program that calls both an `HttpWire` builtin and a builtin `HTTP` one does not fall back: `src/lower.rkt` marks its `LOWER-UNSUPPORTED` as "no fallback" and `src/main.rkt` reports it (exit 1), also under `--legacy-eval` and `agentica test` (§30.8; no new code). Tests: `vm/tests/http_parse_test.c` (the adapter and decoder over the whole hostile list of §10.6), golden fixtures where a program serves raw requests to itself over `TCP`, and `tests/vm-http-test.rkt` with a Python raw-socket peer on port 0 sending every hostile case and checking the status and the close. Add picohttpparser to `.gitmodules`, the release's license files, and the `vm-sanitizers` path list in `.github/workflows/ci.yml`. Docs: `docs/grammar.md` (an `HttpWire` part, marked as the low-level layer; reserved names `HttpWire`, `HttpRequest`, `HttpResponse`), `docs/vm/10-io-tls-processes-http.md` §10.6 and §10.7 (as built), `docs/vm/12-testing-and-pr-plan.md` §12.3, the programming skill's `references/network.md` (one short note: programs use `std/http`, which lands in 20d), the development skill (`references/vm.md`), CHANGELOG ("Added").
- [ ] 20b **Client wire and pool** (§30.3, §30.5). The `HttpClient` handle in C: idle keep-alive connections per scheme, host and port, at most `max_connections` per origin, a FIFO of waiting calls, one `SSL_CTX` per client built once from `ca_file` (system trust when empty); `HttpWire.client`, `HttpWire.exchange` (lease or connect over TCP or the VM's TLS, request head checks, `Host` and `Content-Length` added, the body written while the response is read, interim responses, 101 rejected, the whole body decoded within `max_body_bytes` from `Content-Length`, chunked or close-delimited framing, UTF-8 checked, the connection returned only after a complete exchange; one timeout for the whole call) and `HttpWire.close_client`. Tests: golden fixtures against a server written in the fixture over `TCP` (keep-alive reuse, `Connection: close`, a body over the limit, a non-UTF-8 body); in `tests/vm-http-test.rkt`, Python `http.server.ThreadingHTTPServer` and an HTTPS server with Python's `ssl` and `tests/fixtures/tls/` (chunked and close-delimited bodies, a slow server and the timeout, `max_connections` waits, a server that answers 413 early to a large upload), and the client-side hostile responses of §10.6 from the raw peer. Docs: `docs/grammar.md` (`HttpWire` client part), `docs/vm/10-io-tls-processes-http.md` §10.7, `docs/vm/12-testing-and-pr-plan.md` §12.3, the development skill, CHANGELOG ("Added").
- [ ] 20c **Server task group and task cancellation** (§30.6). Parent and children links on each task (a task's running children move to its parent when it ends) and `agc_task_cancel` for a ready task, a task parked on an I/O job (detached: it ends on its own deadline, its result is dropped, the handle is not closed by it), a task waiting for a handle's lock (`next_owner` passes on), a task in `Task.await` and a task in `Task.sleep`; tasks awaiting a cancelled task halt with `RUNTIME-TASK-CANCELLED` at their own span. No public API: this is the core that §27.1 planned for 17a, which then reuses it and adds the `Task.map` and channel states. The `HttpServer` handle: `HttpWire.server`, `accept` (waits for a free slot; an error only after `close_server`; other accept failures retried in C; a TLS socket is returned before its handshake, which runs in the first `read_request`), `spawn` (a group task that owns its socket), `close_server` (closes the listener, cancels the group's tasks and their descendants, closes their sockets, wakes `accept` and `wait`; idempotent), `wait` and `local_port`. The TLS socket code learns a pending handshake that runs on the first read or write, under that call's timeout. Tests: a C test of `agc_task_cancel` on each state and of the move of children; golden fixtures of a server loop written in the fixture with `HttpWire` (a handler that sleeps while `close_server` runs never prints its next line, nor does a task it spawned; `wait` returns after `close_server`; `main` returns while handlers run); a Node `http` client test of `max_connections` (one more client waits until a slot frees). Docs: `docs/grammar.md` (`HttpWire` server part), `docs/vm/10-io-scheduler.md` §10.2.1 and §10.2.2 (task cancellation, detached jobs, the `next_owner` hand-on), `docs/vm/10-io-tls-processes-http.md` §10.7, `docs/vm/12-testing-and-pr-plan.md` §12.3, `docs/future/27-iteration-and-concurrency.md` §27.1 and roadmap 17a (the core is there; 17a extends it), the development skill, CHANGELOG ("Added").

- [ ] 20e **Streamed downloads** (§30.11), order step 7.4, after 17b. `HttpStream(status, headers, body: Channel[String], done: Task[Result[Void]])` and `HTTP.open(client, method, url, headers, body)`: it returns at the response head; a feeder task reads pieces with the new primitive `HttpWire.read_chunk` (at most 64 KiB, split at UTF-8 boundaries, `""` at the end), sends them with the client's `timeout_ms`, closes the channel on every path, and ends with `ok()` or the error; a reader that closes the channel stops it, and the connection is closed, never pooled. Tests: golden fixtures (a body larger than `max_body_bytes` read in pieces, the reader closing early, `done` after a clean end); in `tests/vm-http-test.rkt`, a Python server that sends a slow chunked body and one that resets mid-body (`done` gives the error). Docs: `docs/grammar.md`, `references/network.md` (the one-form-per-job table of §30.11), `site/content/library/network.md`, `docs/vm/10-io-tls-processes-http.md` §10.7, the development skill, CHANGELOG ("Added").
- [ ] 20f **Streamed uploads** (§30.11), order step 7.4. `HTTP.upload(client, method, url, headers, length, body: Channel[String]) -> Result[HttpResponse]`: `length` is the exact byte count or -1 for chunked; a body that ends short or long is an `error`; the response is whole. C gets the chunked encoder back for requests (`HttpWire` upload primitives). Tests: golden fixtures (fixed length, chunked, a wrong length), and Python and Node servers in `tests/vm-http-test.rkt` that read the chunked upload and one that answers early. Docs: as 20e, CHANGELOG ("Added").
- [ ] 20g **Streamed responses and SSE** (§30.11), order step 7.4. `HttpStreamResponse(status, headers, body: Channel[String])`, `HTTP.listen_stream(host, port, handler, options)`, `HTTP.listen_stream_tls(host, port, cert_file, key_file, handler, options)` and `HTTP.whole(text)`: the connection writes chunked (or `Content-Length` for a channel already closed with every piece buffered), writes each piece as it arrives, checks for a client that left on each receive timeout (`idle_timeout_ms`), and closes the channel when it leaves, so the feeder stops. Tests: golden fixtures (an SSE route next to a `HTTP.whole` route, a feeder that ends with an error, a client that leaves), and in `tests/vm-http-test.rkt` a Python `http.client` reading an SSE stream piece by piece and a Node client that disconnects mid-stream. Docs: as 20e, with the SSE pattern in `references/network.md`, CHANGELOG ("Added").
