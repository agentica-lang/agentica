## Phase 20: HTTP on the VM (simple, synchronous, hybrid)

Specified in [`docs/future/30-hybrid-http.md` section 30](../future/30-hybrid-http.md#30-http-on-the-vm-simple-synchronous-hybrid), decided by the user on 2026-10-12. Two parts:

- **20a to 20d, simple HTTP**, are the HTTP part of the catch-up: after TLS on the VM (today's API, roadmap 7h); 20a (done) came before BDD in Agentica ([phase 21](21-bdd-in-agentica.md), [§31](../future/31-bdd-in-agentica.md#31-bdd-in-agentica)). **Changed by the owner on 2026-10-13:** 7i (order step 7.2) came before 20b to 20d and deleted the builtin `HTTP` module with the evaluator, server included, so `HTTP` is the free import alias of `std/http` and only its client (20a) exists; the order is now 7i, 20b, task crash isolation ([phase 24](24-task-crash-isolation.md), §37), unit tests ([phase 25](25-unit-tests.md), §36), then 20c (order step 7.2.1), and 20c brings the server back. The switch that 20d planned was done by 7i; what was left of 20d moved into 20c. They replace roadmap 7h's C-only HTTP item ([`07-vm.md`](07-vm.md)). Whole requests and whole responses, `String` bodies (strict UTF-8, `max_body_bytes` 1 MiB by default, up to 64 MiB), handlers that return `Result[HttpResponse]`, responses always sent with `Content-Length`, and no streaming. C keeps head parsing, whole-body framing and limits, the connection pool and the server's task group (the `HttpWire` builtins, which only `std/` code may call); Agentica (`std/http.agc`, imported as `HTTP`) keeps the rest. The removal of the builtin `HTTP` module is a breaking change, with its migration notes in `docs/grammar.md` and §30.8.
- **20e to 20g, streaming**, are new features at order step 7.4, VM-only: after phase 17 (`Task.map` and channels), since they are built on `Channel[T]` (17b), and right before `TlsContext` (phase 19). Their calls have fixed argument lists, so default parameter values (15a, order step 7.5) never change them.

Each item is one PR that keeps its own tests and docs (the stacked-PR rule), lists the docs it updates, and ticks itself here. Simple HTTP keeps today's TLS parameters (`ca_file`, `cert_file`, `key_file`) until phase 19 changes `TLS` and `HTTP` together.

**Test peers, by role** (decided by the user on 2026-10-13). Where the VM must talk to a real implementation, the peer is one whose library does the protocol work; for raw or hostile cases, it is the language the test file already uses, so each test file has one peer. So the streaming items (20e to 20g) use Node's `http`, which decodes chunked in both directions with its own parser and is event-driven: Python's `http.server` does not decode chunked request bodies, so a Python server reading the VM's chunked upload would parse chunks with our own code, which is not an independent implementation. 20a and 20c keep their planned peers (Python `http.server` and raw sockets, and the Python and Node clients for the server).

- [x] 20c **Server** (§30.3, §30.4, §30.6), the first HTTP server since 7i removed the builtin one. It brings back the builtin records `HttpServerOptions` (with `request_timeout_ms`, not the old `header_timeout_ms`) and the handle `HttpServer`, which 7i deleted with the builtin module, and `examples/http_server.agc` on `std/http` with its CI smoke run. The builtin record `HttpRequest` (body `String`); `HttpWire.read_request` (bounded by `request_timeout_ms` from the request's first byte; 100 Continue, 417, 501 for `CONNECT` and `Upgrade`, 413 for a `Content-Length` over the limit before any 100 Continue, 431, 505, 400 for a non-UTF-8 body, and the error answer written in C before the socket closes) and `HttpWire.write_response` (bounded by a fresh `request_timeout_ms` from the handler's return; the handler's own run has no limit, as today; `Content-Length` always, `HEAD`, 204 and 304, header validation); the `HttpServer` task group: `HttpWire.server`, `accept` (waits for a free slot; an error only after `close_server`; other accept failures retried in C; a TLS socket is returned before its handshake, which runs in the first `read_request`), `spawn` (a group task that owns its socket; the group is a parent node, so the children of a handler that ended move to it), `close_server` (closes the listener, cancels the group's tasks and their descendants with 20b's core, closes their sockets, wakes `accept` and `wait`; idempotent), `wait` and `local_port`; the TLS socket code learns a pending handshake that runs on the first read or write, under that call's timeout. The server part of `stdlib/http.agc` (`server_options`, `listen`, `listen_tls` on `TLS.listen` with today's file paths, the accept loop, the connection loop with keep-alive and handler dispatch, the 500 answers with their stderr lines, `local_port`, `wait`, `close_server`). Tests: golden fixtures with a client and a server in one program (GET, POST, HEAD, 204, 304, 404, a handler `error`, an unsendable response, keep-alive, `Connection: close`, body limits, a non-UTF-8 body, `close_server` while a handler sleeps: its next line and a task it spawned never print, a handler that sleeps longer than `request_timeout_ms` and still gets its reply out, a handler that calls `HTTP.close_server` and then prints: that line never prints and its client sees the connection close with no response, a task left running by a handler that returned is cancelled by `close_server`, `wait` after `close_server`, `main` returning while handlers run); in `tests/vm-http-test.rkt`, every hostile request of §10.6 from a Python raw-socket peer (status and close), `Expect: 100-continue` with a `Content-Length` over the limit (413 and no `100 Continue` seen first), Python `http.client` and Node `http` clients (chunked uploads, `Expect: 100-continue`, pipelined keep-alive requests, `HEAD`, concurrent clients up to `max_connections` and one more that waits). Docs: `docs/grammar.md` (the `std/http` server part; the "no server until 20c" lines go; reserved names `HttpRequest`, `HttpServer`, `HttpServerOptions`), `site/content/library/network.md` and the programming skill's `references/network.md` (the server, `{mode="check"}` where it touches the network), `docs/vm/10-io-scheduler.md` §10.2 (handlers run as tasks), `docs/vm/10-io-tls-processes-http.md` §10.7, `docs/vm/12-testing-and-pr-plan.md` §12.3, the development skill, CHANGELOG ("Added", the 20c text of §30.8). **Done** (two PRs: the server, then the hints, the benchmark and the ticks). As built (`docs/vm/10-io-tls-processes-http.md` §10.7.2): `vm/http_server.c` with header code shared with the client in `vm/http_fields.c`; the group is a task node that never runs (`agc_task_group`), connection tasks start under it (`agc_task_spawn_in`) with an end hook that closes the socket and frees the slot; `close_server` drops the group with `agc_task_drop` (the crash's mark, `agc_task_cancel`, then `agc_close_owned`), so the handles of cancelled handlers and of the tasks they spawned close at once; after an error answer the server shuts its write side and drops input until the peer closes or the request deadline, so the answer is not lost to a reset over unread request bytes; `agc_io_extend` restarts the read job's timer at the request's first byte.
