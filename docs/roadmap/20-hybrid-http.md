## Phase 20: HTTP on the VM (simple, synchronous, hybrid)

Specified in [`docs/future/30-hybrid-http.md` section 30](../future/30-hybrid-http.md#30-http-on-the-vm-simple-synchronous-hybrid), decided by the user on 2026-10-12. Two parts:

- **20a to 20d, simple HTTP**, are the HTTP catch-up of order step 7.1: after TLS on the VM (today's API, roadmap 7h) and before BDD in Agentica ([phase 21](21-bdd-in-agentica.md), [§31](../future/31-bdd-in-agentica.md#31-bdd-in-agentica)), then 7i. They replace roadmap 7h's C-only HTTP item ([`07-vm.md`](07-vm.md)). Whole requests and whole responses, `String` bodies (strict UTF-8, `max_body_bytes` 1 MiB by default, up to 64 MiB), handlers that return `Result[HttpResponse]`, responses always sent with `Content-Length`, and no streaming. C keeps head parsing, whole-body framing and limits, the connection pool and the server's task group (the `HttpWire` builtins, which only `std/` code may call); Agentica (`std/http.agc`, imported as `HTTP`) keeps the rest. 20d is a breaking change made during the catch-up (§30.8).
- **20e to 20g, streaming**, are new features at order step 7.4, VM-only: after phase 17 (`Task.map` and channels), since they are built on `Channel[T]` (17b), and right before `TlsContext` (phase 19). Their calls have fixed argument lists, so default parameter values (15a, order step 7.5) never change them.

Each item is one PR that keeps its own tests and docs (the stacked-PR rule), lists the docs it updates, and ticks itself here. Simple HTTP keeps today's TLS parameters (`ca_file`, `cert_file`, `key_file`) until phase 19 changes `TLS` and `HTTP` together.

- [ ] 20a **Client, and the guards** (§30.3, §30.4, §30.5, §30.8). - [ ] 20b **Task cancellation core** (§30.6), C only, no public API. Parent and children links on each task (a task's running children move to its parent when it ends) and `agc_task_cancel` for a ready task, a task parked on an I/O job (detached: it ends on its own deadline, its result is dropped, the handle is not closed by it), a task waiting for a handle's lock (`next_owner` passes on), a task in `Task.await`, a task in `Task.sleep`, a task waiting in an `HttpClient` pool FIFO (it leaves the queue; a slot reserved for it passes to the next waiter or becomes free), and a running task, including the one that calls the cancel (its flag is set and it stops at the next safe point after the current builtin returns; with N schedulers, the cancel flag of `docs/vm/10-io-multicore.md` §10.2.3); tasks awaiting a cancelled task halt with `RUNTIME-TASK-CANCELLED` at their own span. - [ ] 20c **Server** (§30.3, §30.4, §30.6). The builtin record `HttpRequest` (body `String`); `HttpWire.read_request` (bounded by `request_timeout_ms` from the request's first byte; 100 Continue, 417, 501 for `CONNECT` and `Upgrade`, 413 for a `Content-Length` over the limit before any 100 Continue, 431, 505, 400 for a non-UTF-8 body, and the error answer written in C before the socket closes) and `HttpWire.write_response` (bounded by a fresh `request_timeout_ms` from the handler's return; the handler's own run has no limit, as today; `Content-Length` always, `HEAD`, 204 and 304, header validation); the `HttpServer` task group: `HttpWire.server`, `accept` (waits for a free slot; an error only after `close_server`; other accept failures retried in C; a TLS socket is returned before its handshake, which runs in the first `read_request`), `spawn` (a group task that owns its socket; the group is a parent node, so the children of a handler that ended move to it), `close_server` (closes the listener, cancels the group's tasks and their descendants with 20b's core, closes their sockets, wakes `accept` and `wait`; idempotent), `wait` and `local_port`; the TLS socket code learns a pending handshake that runs on the first read or write, under that call's timeout. The server part of `stdlib/http.agc` (`server_options`, `listen`, `listen_tls` on `TLS.listen` with today's file paths, the accept loop, the connection loop with keep-alive and handler dispatch, the 500 answers with their stderr lines, `local_port`, `wait`, `close_server`). Tests: golden fixtures with a client and a server in one program (GET, POST, HEAD, 204, 304, 404, a handler `error`, an unsendable response, keep-alive, `Connection: close`, body limits, a non-UTF-8 body, `close_server` while a handler sleeps: its next line and a task it spawned never print, a handler that sleeps longer than `request_timeout_ms` and still gets its reply out, a handler that calls `HTTP.close_server` and then prints: that line never prints and its client sees the connection close with no response, a task left running by a handler that returned is cancelled by `close_server`, `wait` after `close_server`, `main` returning while handlers run); in `tests/vm-http-test.rkt`, every hostile request of §10.6 from a Python raw-socket peer (status and close), `Expect: 100-continue` with a `Content-Length` over the limit (413 and no `100 Continue` seen first), Python `http.client` and Node `http` clients (chunked uploads, `Expect: 100-continue`, pipelined keep-alive requests, `HEAD`, concurrent clients up to `max_connections` and one more that waits). Docs: `docs/grammar.md` (the `std/http` server part, with the same status line; reserved name `HttpRequest`), `docs/vm/10-io-tls-processes-http.md` §10.7, `docs/vm/12-testing-and-pr-plan.md` §12.3, the development skill, CHANGELOG ("Added", the 20c text of §30.8).

- [ ] 20e **Streamed downloads** (§30.11), order step 7.4, after 17b. `HttpStream(status, headers, body: Channel[String], done: Task[Result[Void]])` and `HTTP.open(client, method, url, headers, body)`: it returns at the response head; a feeder task reads pieces with the new primitive `HttpWire.read_chunk` (at most 64 KiB, split at UTF-8 boundaries, `""` at the end), sends them with the client's `timeout_ms`, closes the channel on every path, and ends with `ok()` or the error; a reader that closes the channel stops it, and the connection is closed, never pooled. - [ ] 20f **Streamed uploads** (§30.11), order step 7.4. `HTTP.upload(client, method, url, headers, length, body: Channel[String]) -> Result[HttpResponse]`: `length` is the exact byte count or -1 for chunked; a body that ends short or long is an `error`; the response is whole. - [ ] 20g **Streamed responses and SSE** (§30.11), order step 7.4. `HttpStreamResponse(status, headers, body: Channel[String])`, `HTTP.listen_stream(host, port, handler, options)`, `HTTP.listen_stream_tls(host, port, cert_file, key_file, handler, options)` and `HTTP.whole(text)`: the connection writes chunked (or `Content-Length` for a channel already closed with every piece buffered), writes each piece as it arrives, checks for a client that left on each receive timeout (`idle_timeout_ms`), and closes the channel when it leaves, so the feeder stops.
