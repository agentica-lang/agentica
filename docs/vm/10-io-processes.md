### 10.4 Processes

- `--allow-run` is the VM's own flag, checked inside `Process.spawn` at call time, for every task and handler.
- The VM resolves the executable itself, with the rule of the grammar (Processes): a command with `/` resolves against the program's working directory, and a bare name is looked up in each `PATH` entry in order. Empty entries are skipped, and an explicit relative entry such as `.` resolves against the working directory. The VM never adds the working directory itself. It passes the absolute path to `uv_spawn`. All three stdio streams are pipes. `UV_PROCESS_WINDOWS_VERBATIM_ARGUMENTS` is never used.
- A child must not get `UV_USE_IO_URING=0` from the VM's own environment (§10.2.2), unless the user set it before the VM started.
- Windows (not built): allow only `.exe` and `.com` after resolution, case-insensitively, and reject names with a trailing dot or space or any `:`. The allowlist applies to the last component of the resolved path. The port must not search the current directory before `PATH`.

**As built (processes PR, Linux).** `vm/process.c` holds the eight `Process` builtins. Other systems get none.

- **Values.** A `Process` has a registered state and two lock records, `reader` and `writer`. `read_line` and `read_bytes` take the reader lock. `send`, `send_bytes` and `close_stdin` take the writer lock. `wait` and `close` take neither. A reader parked on a silent child never blocks a writer, and a lock-wait timeout leaves the process running.
- **Spawn.** Checks, in order: `--allow-run`; a nonempty command with no NUL; the timeout. A path that does not exist, or is a directory, gives `process: executable is unavailable`. The pipes are real pipes, not socketpairs. The first spawn marks every inherited descriptor above 2 close-on-exec, so a child sees only 0, 1 and 2. A failed `uv_spawn` (`EACCES`, `ENOEXEC`) is an error `Result` with the OS text.
- **Parking.** Operations park only their task, with the call's timeout. Stdout is read only while a reader waits, 4 KiB at a time (more when `read_bytes` needs more), so the VM reads at most about 4 KiB past what the program asked. A child that writes more than the program reads blocks on its pipe. A read error after a partial line returns the error, not the partial line. `wait` returns when the child has exited and its stderr is at EOF. A timed-out read or write closes the process. A timed-out `wait` leaves the child running.
- **Stderr** is read all the time, and each chunk goes to the program's stderr at once, so it keeps its order with `IO.warn`. If that write fails (`/dev/full`, say), the rest is read and dropped, and the child is kept.
- **Close.** `Process.close`, a timed-out read or write, the end of the run (step 1 of §14.4) and a stop signal share one close: a running child gets `SIGKILL`, and libuv's exit callback reaps it (no `waitpid`, no sleep). The pipes close at once, and a task blocked on the child (reader, writer or waiter) wakes with `process: process is closed`. Only the call that parks waits: `Process.close` of a running plain child parks its task on a job with a 1-second timer, which the exit callback ends, and other tasks run meanwhile, so those blocked tasks wake before it returns. A second `Process.close` returns at once. Owned closes do not wait: a timed-out read or write (its timeout error stands), an oversized line, and the close of a task that crashes or of a server dropped by `close_server` only send the signal, so a respawn right after a read timeout may briefly overlap the old child. The end of the run and a stop signal send `SIGKILL` to every child, then run the loop until the exit callbacks have run, under a 1-second bound, once per run, inside the driver's 2-second grace (`docs/vm/08-loader-and-cli.md` §9). A child that cannot be killed (`EPERM`) is not waited for, and one that sleeps uninterruptibly is waited for only up to the bound: libuv reaps it later, or `init` gets it after `_exit`. A failed kill in `Process.close` ends the run with `RUNTIME-PROCESS-CLOSE`. Later operations on a closed process return `process: process is closed`.
- **Signals.** A stop signal takes the one exit path (§10.2.2): children are killed and reaped, files are flushed, and the signal is raised again. Children are killed before the file flush. A VM killed by `SIGKILL`, or ended by the out-of-memory exit (70, §6.3), leaves its children running. On a break, `agentica` waits 2 seconds, sends `SIGTERM`, and kills the VM 2 seconds later (`docs/vm/08-loader-and-cli.md`).
- **Behavior notes.**
  - A file that exists but cannot be executed (no execute permission, a bad format) is an error `Result` from `Process.spawn`.
  - A `read_line` or `read_bytes` pending in another task when the process is closed returns `process: process is closed`.
  - libuv resets signals 1 to 31 to their default in the child, so a signal the VM inherited as ignored (`nohup`) is not ignored in its children. The VM does not patch libuv.
  - `Process.spawn` checks its timeout but does not apply it to the lookup and start.

**As built (21a, captured processes, Linux).** `Process.spawn_captured` and `Process.output` (specified in `docs/grammar/06d-io-and-network.md`) share the code above.

- **Spawn.** The checks keep the order above, with `dir` (nonempty, no NUL) checked after the arguments and before the timeout. `dir` must be a directory, else `process: directory is unavailable`. `"."` passes no working directory.
- **Reading.** Both pipes are read from the spawn on and never stopped. Pending bytes are capped at 1 MiB. A byte that does not fit marks its stream as cut, and later chunks of that stream are read and dropped, so the child never blocks. The stdout limit counts unread bytes. Stderr keeps its first 1 MiB.
- **Output.** `Process.output` is a wait that is ready when stdout is at EOF or has a read error, and stderr is at EOF. The record is built from the pending bytes, with U+FFFD for invalid UTF-8, and nothing is consumed. It charges a turn cost by the bytes it copies.
- **Close.** `shut` sends `SIGTERM` to a running captured child and starts a 1-second grace timer. The pipes close, and the program sees `process: process is closed` at once. When the timer fires, `SIGKILL` is sent, and libuv reaps the child, so `Process.close` never blocks. At the end of the run and on a stop signal, plain children get `SIGKILL`, captured ones get `SIGTERM` (if not sent yet), the loop runs until the captured ones have exited, under one 1-second bound, and the rest get `SIGKILL` and the loop runs until they have exited, under another 1-second bound. `Process.close` of a captured child does not park. A child that handles `SIGTERM` ends the cleanup in milliseconds. A failed `SIGTERM` in `Process.close` is `RUNTIME-PROCESS-CLOSE`.

**As built (25c, the child channel, Linux only).** A second pipe, separate from stdin, stdout and stderr, carries the protocol of `agentica test` and of BDD children, so a test or a step program owns its own stdin and stdout. `Process.spawn_channel`, `channel_read_line`, `channel_send`, `channel_close` and `read_available` are in `vm/process.c`; `Process.parent_read_line` and `Process.parent_send` (the child side) and the shared duplex stream are in `vm/duplex.c`, a service (`docs/vm/15-layers.md`). The signatures are in `docs/grammar/06d-io-and-network.md`. Other systems build none of them (the VM has `_WIN32` paths): the channel is Linux only.

- **The pipe.** One `uv_socketpair` (`SOCK_STREAM`) per child. The parent keeps one end as a libuv pipe handle, and the child gets the other as descriptor 3 (`stdio[3]`, so `stdio_count` is 4) and the variable `AGENTICA_CHANNEL=3`. A socket and not a FIFO, so the child cannot reopen it through `/proc/self/fd/3` with a different mode, and one object carries both directions. The stream is text lines in both directions, as in the other `Process` streams: `\n` ends a line, a trailing `\r` is removed, a last line without `\n` is a line, and invalid UTF-8 is an error.
- **Environment.** Every spawn builds the child's environment from the VM's own: `AGENTICA_CHANNEL` is always removed, `UV_USE_IO_URING` is removed as before (§10.2.2), and only `spawn_channel` adds `AGENTICA_CHANNEL=3`. So a parent that spawns without the pipe never passes an inherited marker on, and a grandchild sees neither the marker nor descriptor 3 unless its own parent opened a channel for it.
- **Child start.** `agc_parent_take` runs in `main.c` before the program does. If `AGENTICA_CHANNEL` is `3` and `fstat(3)` says socket or FIFO, the VM moves the descriptor with `F_DUPFD_CLOEXEC`, closes 3, forgets it in the table of inherited files (so no `File` call can reach it), removes the variable from its own environment, and keeps the stream until the end of the run. In any other case nothing is touched and the child-side builtins return `error("process: no parent channel")`. The libuv handle is attached on first use, so a program that never uses the channel never starts a read.
- **Locks and waits.** A parent-side `Process` has two more lock records, `channel.reader` and `channel.writer`, so a `channel_read_line` parked on a silent child blocks neither `Process.read_line` nor `send` (§14.1); the child side has one pair for the VM (`vm->parent_locks`). Every operation is a job on the loop with its timeout as the job timer (§14.2): `timeout_ms` must be positive on both sides (else the error of the other stream builtins), and it includes the lock wait. A second reader (or writer) of the same end waits on the lock. `Process.parent_read_line(timeout_ms)` and `Process.parent_send(text, timeout_ms)` take a timeout like their parent-side twins; there is no untimed form.
- **Timeouts and errors.** A timed-out `channel_read_line` or `channel_send` closes the channel and only the channel: the process keeps running, so the parent can still call `read_available`, `output`, `wait` and `close`. Later channel calls return `error("process: channel is closed")`. The same holds for the child side. `channel_read_line` at the end of the child's output returns `error("process: end of input")` (a reset peer counts as the end); a line over 1 MiB is `error("process: line exceeds 1048576 bytes")` and closes the channel; `channel_send` takes at most 1048576 bytes (`process: send exceeds 1048576 bytes`) and a write that finds the peer gone is the OS error text. On a process made by `spawn` or `spawn_captured`, the three parent-side channel calls return `error("process: the child has no channel")`; on a closed process they return `error("process: process is closed")`.
- **Half close.** `channel_close(p, timeout_ms)` shuts the write side only (`uv_shutdown`): the child reads the end of its input, and the parent can still read what the child sends. It is idempotent.
- **`read_available`.** Returns, as a `String`, the stdout the VM has captured since the last call and consumes it. It never waits for more output: `timeout_ms` bounds only the wait for the reader lock. Before it answers, it drains the stdout pipe with non-blocking reads, so everything the child wrote to stdout before it wrote a channel line is in the text once that line has been read. That is the whole ordering rule between the two streams: a child that flushes its stdout before it sends a channel record (the VM does, in `Test.run` and in `BDD`) gets that output attributed to that record. It returns `error("process: output exceeds 1048576 bytes")` once stdout or stderr was cut (more than 1 MiB unread, as above), and `error("process: output is not captured")` on a `spawn` handle. A cut that happens between two calls is how the runner finds a test that printed more than 1 MiB.
- **Close.** The channel handle closes with the process (`shut`), after the pipes. A pending channel read or write wakes with `process: channel is closed`.
- **`Test.run` and the BDD children** use the child side. `Test.run` takes the channel once (`agc_parent_claim`): a second call, in a test or in another task, is `RUNTIME-TEST-RUN`, and so is a call with no channel under `--agentica-test list|run`. It flushes stdout (`agc_drain`) before each record, then sends the record as one JSON line with `agc_parent_send`. The core has no protocol mode: stdout is an ordinary stream and stdin is the program's.

### 10.5 Limits the C runtime keeps

| Limit | Value |
|---|---|
| `IO.read_bytes` count | 0..1 MiB |
| Process send, read, line | 1 MiB |
| File read, line, text, writes | 1 MiB |
| TCP `send_bytes`, `recv_bytes`, line (`TCP.send` of a String has no limit, as in the grammar) | 1 MiB |
| Byte values | 0..255 |
| `List.repeat` count | 0..1048576 |
| HTTP start and header line | 8192 bytes |
| HTTP header block | 65536 bytes |
| HTTP headers | 100 |
| HTTP interim responses | 15 accepted, the 16th fails |
| `max_connections` | at most 65536 |
| HTTP body | `max_body_bytes`, 413. The body is held whole, so the default is 1 MiB and the cap 64 MiB (10.7) |
| Process launch | `--allow-run` |
| Windows programs other than `.exe`, `.com` | rejected |

HTTP numbers: `Content-Length` and chunk sizes accumulate with saturation. Parsing stops once a value exceeds the limit (413), and every comparison is written `size > limit - total`.
