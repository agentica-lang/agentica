### 10.2 Rules for 7h

The core rules (waiting, timeouts, cancelling, ending, handles) are in §14. This section says how the scheduler and the loop keep them, as built.

- **Target.** N scheduler threads run the interpreter and pull ready tasks from one global run queue. One I/O thread, the main thread, runs the only libuv loop (10.2.3, §16). The built VM runs N=1: the scheduler and the loop share one thread.
- **Tasks are VM stacks.** A blocking builtin starts a libuv request, parks its task, and the scheduler runs another (10.2.1). Only the loop's thread calls `uv_run`. libuv callbacks only copy results and mark tasks ready. With N>1, TLS and HTTP parsing run on the scheduler that resumes the task (§16.2). Output order across tasks is not defined.
- **Blocking output and files.** Stdout and stderr stay blocking writes (§14.1). The VM never sets the thread pool size (10.2.2, Pool size).
- **Thread-pool threads never touch GC memory.** Requests and handles are `malloc`'d, and file buffers are `malloc`'d copies. The GC object that owns a handle stays registered until its `uv_close` callback. `handle->data` and `SSL_set_app_data` point to GC objects only while registered. `CRYPTO_set_mem_functions` is never routed to the GC.
- **Descriptors are non-inheritable.** All VM file descriptors and handles are `O_CLOEXEC`.

#### 10.2.1 Scheduler

- **Run queue.** One FIFO of ready tasks, ordered by the scheduler alone: libuv never decides which task runs. A new task, a task whose turn ended, and a task woken by a libuv callback go to its back. With N>1 it is the global run queue, under its lock (§16.3, 10.2.3).
- **Reductions.** Each turn has a budget of 2000 steps (`AGC_TURN_STEPS`), counted by `STEP` as `--max-steps` counts them (`STEP n` counts n). When a `STEP` spends the budget, the task goes to the back of the queue. A merged `STEP n` that crosses the budget charges all n and yields at the next instruction; the excess is not carried over. Crossing `--max-steps` fails the task with `RUNTIME-STEP-LIMIT` at the span of 4.2. The scheduler switches only at a `STEP`, at a safe point, or right after a builtin or opcode whose turn cost spent the budget (Builtins). Every loop passes a `STEP`, and every function that calls starts with one (8). A task also leaves its turn when it blocks.
- **One counter for both budgets.** `STEP` counts down one "next stop" counter, set to `min(turn_left, batch)` when a turn starts and after each sync, where the batch is the part of `steps_left` the scheduler holds (Quotas). Turn costs never touch it, so the fast path is one compare and one subtraction. The sync cannot fail, since the counter is never above the batch, and a turn cost is charged once and then cleared. Neither the `STEP` slow path nor the turn-cost path reads the cancel or stop flags; the scheduler reads them after each turn (`vm/task.c`).
- **Builtins.** No builtin's C code is stopped halfway. A resumable builtin (4.3: `map`, `filter`, `reduce`, `each`, `any?`, `all?`, `sort_by`) can be switched out only between its callbacks. Any other builtin finishes its turn, so a builtin whose work grows with its input charges a **turn cost**: one unit per item (a sort counts n·⌈log2 n⌉) and one per 64 bytes it copies or scans. Constant work charges nothing. Some opcodes charge the same way: string concatenation, interpolation, `to_s`, `inspect`, string equality (the checker allows `==` only on scalars, strings and ranges), and map access with String keys. The turn cost comes from the turn only, never from `--max-steps` (`steps_left`). The task yields at the next instruction if its turn is spent. File builtins charge nothing: their work is I/O, at most 1 MiB per call.
- **Test switch.** `AGENTICA_VM_TEST_NO_TURN_COST=1` skips the turn-cost charge. It changes only when tasks switch, never output, step counts or diagnostics. It is for tests only, so the latency test (`make vm-latency`) can show that it fails without the rule.
- **Fairness with I/O.** After each turn the scheduler calls `uv_run(UV_RUN_NOWAIT)`, so ready I/O and timers wake their tasks while others compute. Tasks woken during a `NOWAIT` go behind the queued ones. With N=1 it blocks in `uv_run(UV_RUN_ONCE)` only when its queue is empty. A ready event waits at most for the turns queued ahead of it, each about one budget plus the last builtin call of that turn. The latency test checks this next to CPU-bound tasks. A parked task waits on I/O, a timer, another live task, or a channel, with a timer.
- **Quotas.**
  - `--max-steps` is one global budget shared by all tasks (`steps_left`, 6.1), and turn costs are never charged to it. With one task, a runaway program stops with `RUNTIME-STEP-LIMIT`. With several, which task fails depends on the interleaving, and tests do not compare it.
  - With N schedulers, `steps_left` is one atomic counter. A scheduler takes a batch per turn and gives back the unspent part when the turn ends, the task parks, or the scheduler goes idle. With N=1 the counts are exact. With N>1 the run may stop up to (N-1) turn budgets early.
  - Per-task step quotas are not in 7h. Per-task memory quotas are out of scope, since the Boehm heap is shared. Only a global heap limit is possible (13).
- **As built (tasks PR).** `vm/task.c` holds the scheduler and the `Task` builtins. `vm/interp.c` runs one turn and owns the budget code.
  - `Task.sleep(0)` yields. `Task.sleep(n)` is a timer-only job. Under `no_files` (the fuzzer) every sleep yields.
  - Stdin EOF is delivered once to every task that waited for the read, so a TTY reader never waits for a second Ctrl-D.
  - `Task.await` parks the caller with *retry*: when the target ends, each waiter re-runs its builtin and gets the cached result. Stdin reads use the same retry (a wake is only a hint, 10.2.3). A task whose bottom frame returns, or leaves through `try`, is done.
  - **Await cycles (17b).** A task can receive its own handle over a channel, or hide it in a closure, so awaits can form a cycle. Each task waits on at most one task (`awaiting`). Before `Task.await` parks, it follows the chain from the target through the `awaiting` fields. If the chain reaches the caller, the call fails with `RUNTIME-TASK-AWAIT-CYCLE` at the `Task.await` span and the caller does not park. A task that awaits its own handle is the shortest cycle. The walk is one turn-cost unit for each hop.
  - When `main` returns, ready and parked tasks never run again, and the exit path (End of run) does not wait for their jobs. `System.exit`, a failure in `main`, `RUNTIME-STEP-LIMIT` or `RUNTIME-INTERNAL` in any task end the run at once.
  - **Crashes (phase 24, `docs/future/37-task-crash-isolation.md` §37).** Any failure in a task other than `main` crashes that task. The text `task crashed: CODE at FILE:LINE:COLUMN: MESSAGE` joins the run's unobserved crashes. Crashes of `hidden` tasks (the HTTP connection tasks of 20c) join only the first per test (or per run outside `Test.run`); the others count as `quiet_more`, so the list stays bounded. The diagnostic goes to stderr with ` in a task` (`"task":true` in `--json`). The task leaves its jobs, locks and FIFOs as a cancelled task does, its subtree is cancelled and marked, and every handle an owner in that subtree holds is closed (Owners). The task then ends like a returning task, and its awaiters wake.
    `Task.await` halts with `RUNTIME-TASK-CRASHED` (the crash text) or `RUNTIME-TASK-CANCELLED`. `Task.await_result` (used when `R` is a `Result`) returns `error(text)` or `error("task: cancelled")`. Either entry marks the crash observed. If `main` returns with a crash no await observed, the run prints one summary line and exits with code 1.
  - **Owners (phase 24).** The task that makes a user-visible handle owns it, and its kind's close is recorded with it. A socket, listener or TLS socket is disowned on a crash. A process closes with `shut`, which only signals (§10.4 Close), never with the release that would kill every child. The process guard, job resources, stream locks and `HttpClient` have no owner. A handle passed as the `Task.spawn` argument moves to the new task when the caller owns it. A file that is closing gives every caller the closed error. A file's close is an `OP_CLOSE` job with no task: while another job holds the file, it waits and runs when that job ends, also for a detached job. A handle made outside a turn has no owner, and is closed when its result is dropped. When a task ends normally, its handles go to its parent, so a handle returned by a helper task is still closed if the parent crashes later. A cancelled task's handles are neither given back nor closed, except under `close_server` (20c).
  - **Cancellation (20b).** A program cancels tasks only through a crash, which cancels the crashed task's descendants, and through `HTTP.close_server`. Each task records its parent and its running children, and a task that ends hands its running children to its parent. A group node (20c) never runs and has no id: it parents an `HttpServer`'s connection tasks, so cancelling the group reaches them. Cancelling a task cancels its running descendants, children first. A cancelled task gets its flag, then: a ready task leaves the run queue; a parked task detaches from its job (Detached jobs); a task waiting for a handle's lock leaves the FIFO, and passes ownership on if it was the `next_owner`; a task waiting on a channel leaves its FIFO, closes its timer job (Detached jobs), and hands on a reservation it holds (Channel waits); a task in `Task.await` or a stdin wait leaves its FIFO. The task then ends like a returning task. A later `Task.await` on it halts with `RUNTIME-TASK-CANCELLED` (the `Result` entry returns `error("task: cancelled")`). A program can reach it, since a task can send its child's handle over a channel and then crash. A task that cancels itself finishes its builtin and then ends, so no instruction of it runs after that. A cancel spends no step and charges one turn unit per cancelled task, to the caller.
- **Stall check (N=1).** If the queue is empty, no libuv handle is alive, and `main` is not done, the VM fails with `RUNTIME-INTERNAL` ("every task is waiting and nothing can wake them"). No program reaches it: every channel wait holds a timer, every other wait holds a libuv request or a timer or a live task, and await cycles halt before they park (`Task.await` below). For N>1 see 10.2.3.
- **Multi-task runs.** A runaway multi-task run must stop with `RUNTIME-STEP-LIMIT` (the black-box rule, §1). The `--max-steps` sweep (§12.1) needs each limit to give the full outcome, or the step limit with stdout a prefix of the full run. The task fixtures keep that deterministic: their step counts do not depend on the clock.

#### 10.2.2 The loop

- **Resource registry** (`vm/loop.c`). Every handle, request and job is a GC resource that owns its `malloc` memory and keeps its registry slot until it is released. A `FileHandle` points to its resource. A pending request's job holds the libuv work and timer. The job stays registered until its work has run, its timer is closed, and its result was taken. No GC pointer is stored in `malloc` memory, and callbacks find their job with `offsetof`, never through `handle->data`.
- **Blocking builtins are two halves.** The C builtin checks its arguments, copies what the OS needs into a `malloc`'d request (paths through the rules of 2.8), and starts the job. One `uv_queue_work` covers the whole operation (stat, open, read, close), so the task parks once per call. The call's timeout is the job's timer (a negative timeout starts none; a kind without `work` is a timer only). `CALL_BUILTIN` ends the turn.
- **Waking and parking.** The work and timer callbacks only set flags and put the job on the loop's ready list. After each `uv_run` the scheduler drains that list and queues the tasks. After each turn it calls `uv_run(UV_RUN_NOWAIT)`. With an empty run queue it calls `uv_run(UV_RUN_ONCE)`, or fails with `RUNTIME-INTERNAL` when nothing is alive (Stall check). On completion the `done` half runs on the interpreter thread and builds GC values from the `malloc`'d result. On timeout the `expired` half gives the call's timeout error (`filesystem: operation timed out` for a file) and, for a handle operation, closes the handle.
- **Thread-pool threads** run only the `work` half, on `malloc` memory. `UV_USE_IO_URING` is set to `0` (unless already set) before the loop is made, so libuv uses its thread pool and epoll. `SIGINT`, `SIGTERM` and `SIGHUP` are blocked around every pool start, and in the `tcp.c` and `http_client.c` threads, so the stop handler, which may run on any thread, touches only lock-free atomics and async-signal-safe calls.
- **Pool size.** The VM never sets it. libuv's `UV_THREADPOOL_SIZE` does (there is no `AGENTICA_*` variable). It is read once, when the pool is created, so it must be set before the VM starts. The default is 4, and the cap 1024. The pool runs regular-file I/O, opens and path calls, DNS (`getaddrinfo`), and the TLS setup jobs. Nothing that can wait forever runs there.
- **We only wait where the loop can cancel** (§14.1). Files open with `O_CLOEXEC` and `O_NONBLOCK`, so opening a FIFO never waits for a peer. The pool job then picks the path by `fstat` and an `epoll_ctl` probe, never by name. A regular file, a block device, or a device epoll refuses with `EPERM` (`/dev/null`, `/dev/zero`) is blocking, in the pool. Any other probe error is the call's error, never a fall back to blocking. A pipe, FIFO, terminal or other waiting character device is non-blocking on the loop through a poller (`uv_poll_t`). A handle call first tries its step on the loop thread. When it would wait, it parks on an `external` job, and the poller's callback repeats the step. A whole-file call opens in the pool, and if the path is pollable, its `more` step keeps the same job and task waiting on the loop. A pool kind with a `cancel` half must have a `more` step, and `start_job` checks it. A poller error is reported by repeating the step, so the call gets the real error (`EPIPE` for a reader that left). `read_text` of a pipe, or of a regular file that reports size 0 (`/proc`, `/sys`), reads to EOF, at most 1 MiB.
- **End of run: one exit path.** However the run ends (`main` returns, `System.exit`, a runtime error, the step limit, a stop signal), `end_run` in `vm/main.c` takes the same steps and nothing else (§14.4):
  1. kill the children and drive the loop until libuv's exit callbacks have reaped them (10.4, Close; at most about 2 seconds);
  2. one non-blocking TLS `close_notify` on each TLS session that finished its handshake: TCP sockets (10.3) and `HttpClient` connections (10.7.1);
  3. flush stdout and stderr (retried on `EINTR`), close every open file, and wait for their flush jobs. The wait is always bounded: 30 seconds by default, or `--flush-timeout MS`, or the environment variable `AGENTICA_FLUSH_TIMEOUT_MS` (the flag wins; there is no way to turn the limit off), so a FIFO whose reader stopped cannot keep the run open for ever. When it runs out, the VM prints `agentica: file data may not be written: the flush took longer than MS ms` (or `{"flush_timeout_ms":MS,"warning":...}` with `--json`); the exit code does not change;
  4. print the diagnostic or summary, and end with `_exit`, so libuv's destructor never joins the pool.
  No task is awaited, no other pool job is waited for, and no socket is read to its end. Killing the children first means data buffered for a FIFO's reader is lost. A file close that fails at this point prints `agentica: file data may not be written: the flush failed (CODE: message)` (or `{"flush_failed":"CODE","warning":...}`); the exit code does not change. `agc_io_close`, which closes every resource and frees the loop, is only for the in-process harnesses.
- **Stop signals.** One `sigaction` handler covers `SIGINT`, `SIGTERM` and `SIGHUP`, except a signal the VM started ignored (`nohup`). Its state is one process-wide variable (`stop` in `vm/loop.c`, lock-free atomics). The first signal is stored and wakes the loop. The scheduler checks it after every turn, before it waits and before it reports a stall, and the run ends as an exit with code 128 + signal. `end_run` runs the steps above, then raises the signal again with its default action.
  A second signal ends the VM at once, but never before the children are stopped: until then it is only recorded. A 3-second `alarm` (`STOP_GRACE_SECONDS`) backs this up. A driven VM (`--driver-pid`) whose driver is gone treats even the first signal as a second one. The handler has no `SA_RESTART`, so a write to stdout that nobody reads returns `EINTR`. Then the run ends as the stop (128 + signal, no diagnostic). Writes never retry, since a retry would lose the bytes of a failed write. A CPU-bound task delays the stop by at most one turn.
- **Per-handle lock (tasks PR).** A `FileHandle` has a `holder` (the job in flight), a `next_owner` task, and a FIFO of waiting tasks, all in GC memory. Every handle builtin (`read_bytes`, `read_line`, `write`, `write_bytes`, `flush`, `close`) checks its arguments and timeout first, then takes the lock, and only then checks that the handle is open and has the right mode. A task that cannot take the lock parks with retry on a timer-only job that ends at its deadline. One deadline covers the lock wait and the operation: a task that gets the lock after its deadline returns the timeout error. Release is a FIFO hand-off: the head waiter becomes `next_owner` and is the only one woken, so the releasing task cannot take the handle back in the same turn. A cancelled `next_owner` passes ownership on, so a lock never stays with a task that will not run. So `close` waits for the operation in flight, two readers take turns, and buffered writes keep their order. On an operation timeout the stuck operation keeps the state, the handle is closed, and the next owner gets `file handle is closed`.
- **Channel waits (17b, `vm/channel.c`).** A channel is a GC object: a ring buffer, the capacity, a closed flag, and two FIFOs of waiting tasks (receivers and senders) linked through `wait_next`, as the handle lock's FIFO is. The ring starts with at most 8 slots and doubles up to the capacity, so `Channel.new(1048576)` does not allocate a million slots. The copy of a growing ring charges one turn-cost unit per slot copied; other calls charge nothing, and a value is one pointer, never copied. A call that must wait parks with retry on a timer-only job that ends at the call's deadline. The deadline is set at the first wait and kept across retries in the task (`channel.deadline`), as `agc_handle_wait` does. A timeout of 0 never parks: it tries once.
  - **Reservations.** A value that arrives while receivers wait is not put in the ring. The head receiver is popped from its FIFO, the value is stored in the task (`channel.value`), and the task is woken: a direct hand-off, so no other `recv` can take it first. A slot freed by a `recv` while senders wait is reserved for the head sender the same way. Counters in the channel (`reserved_values`, `reserved_slots`) keep `closed?` and the free space exact. A woken waiter re-runs its builtin: with its reservation set it returns the value (or adds its own), even if its deadline passed, since the reservation came first.
  - **A waiter that leaves.** A timer that fires wakes its task and leaves it in the FIFO. The next pop skips a task that is no longer parked, so a reservation never goes to a waiter whose timeout came first. A cancelled waiter (`agc_channel_leave`, called from the task's unlink) leaves its FIFO and hands its reservation on: a value goes to the next waiting receiver, or back to the head of the ring (the ring may then hold more than the capacity until receivers take values, and no value is lost); a slot goes to the next waiting sender, or becomes free.
  - **Close.** `close` marks the channel, revokes the reserved send slots (their `send` returns the closed error and the value is not added), and wakes all senders. Receivers keep getting the values left. A `recv` on a closed channel with an empty ring but a value still reserved for a woken receiver waits, and the receiver that takes the last reservation wakes the others, which then get the closed error. `closed?` is true when the channel is closed, the ring is empty and no value is reserved, and stays true.
  - **Choices.** Mid-FIFO removal is O(n), as for the lock FIFO. A waiter whose timer fired before any wake still takes a value that reached the ring before it re-ran, instead of failing at once.
- **Detached jobs (20b).** When its task is cancelled, a job is detached: it has no task, it is never abandoned with a close, and it runs to its own end or deadline, keeping the handle's lock until then. Its `done` half runs and the result is dropped, not charged to the current task. Its lock passes to the head waiter, as at a release. A handle the dropped result would have handed out is closed then. The `expired` half never runs on a detached job, so it never closes a handle a task holds. A kind may set a `cancel` half, which ends the job early and returns true; no pool kind may have one, since a pool thread may still use the data. `HttpWire.exchange` uses it. An exchange waiting for its TLS setup or a pool slot leaves the queue. One that has sent its request runs to its end, and its connection is then closed, never pooled or retried. For the TCP and process kinds at the deadline, a read, accept or wait leaves its handle without the `expired` half that would close it, a connect closes the socket it was opening, and a send waits for its write callback. A listen has no deadline. A pool job (files, stdin) cannot be stopped, so it ends when its work ends.
- **External jobs.** A kind with `external` set has no `work` half. A libuv callback on the loop thread completes it, which puts the job on the ready list. A second call does nothing.
- **Fuzzing.** `agc_fuzz_one` sets `vm->no_files`: a file builtin (also `Path.cwd` and `Path.resolve`) ends the run with `RUNTIME-INTERNAL`, and `Process.spawn` returns its error. Every loop and resource is released before the mutant ends.
- **Stdin.** Stdin follows the same rule as files. A pipe, FIFO or terminal is reopened through `/proc/self/fd/N` (N is 0, or in protocol mode the reserved descriptor that holds the real stdin) with `O_NONBLOCK`, so the inherited open file description, which a shell's terminal shares, keeps its flags. It is then read on the loop. A socket keeps its flags and is read with `MSG_DONTWAIT`. A regular file, a device epoll refuses, a write-only stdin, a failed reopen (no `/proc`, or `EACCES` after `su` or `sudo -u`), or a failed poller stays a pool job with one blocking `read`, which keeps a pool thread until data comes (§14.1). One read of up to 1 MiB is in flight at a time. A second reader parks in the input's FIFO. A read with no data at the end of the run is not waited for. Non-Linux builds keep the blocking read.
