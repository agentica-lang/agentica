# Pipeline stages reference

Detailed tables for the Agentica Racket front end. Read this when adding or renaming a token, AST node, or diagnostic code.

## Conventions

- A span end is exclusive; offsets count Racket string characters; line and column are 1-based.
- Every stage is `(stage input) -> data | diagnostic`, stops at the first error, and never prints.
- `format-diagnostic` renders a located header, message, source marks/labels, and grounded help. AI and JSON printers consume the same diagnostic data.

## `src/source.rkt`

| Struct | Fields |
| --- | --- |
| `source` | `name`, `text` (opaque) |
| `source-position` | `offset`, `line`, `column` |
| `source-span` | `source`, `start`, `end` |

Accessors: `source-name`, `source-text`, `source-position-offset`/`-line`/`-column`, `source-span-source`/`-start`/`-end`.

## `src/token.rkt`

`(struct token (kind lexeme value span))`. `kind` is a symbol; `lexeme` is the source text; `value` is the decoded literal or `#f`; `span` is a `source-span`.

### Token kinds

| Kind | Lexeme |
| --- | --- |
| `name` | identifier starting with a lowercase letter or `_` |
| `type-name` | identifier starting with an uppercase letter |
| `def` `struct` `enum` `case` `do` `import` `export` `end` `if` `elsif` `else` `while` `for` `in` `return` `try` `true` `false` `nil` `and` `or` `not` | the reserved words |
| `integer` `float` | decimal number literal |
| `string` | decoded string contents |
| `interp-start` `interp-middle` `interp-end` | decoded text before, between and after `#{...}` pieces; the expression tokens come between them |
| `arrow` `equal` `not-equal` `less-equal` `greater-equal` | `->` `==` `!=` `<=` `>=` |
| `left-paren` `right-paren` `left-bracket` `right-bracket` `left-brace` `right-brace` | `(` `)` `[` `]` `{` `}` |
| `comma` `colon` `dot` | `,` `:` `.` |
| `dot-dot` `dot-dot-dot` | `..` `...` (ranges; `1..5` stays two integers, since a Float needs a digit after the dot) |
| `ampersand` | `&` |
| `and` `or` `not` (symbol forms) | `&&` `\|\|` `!` (a `!` glued to a name stays in the name; `!=` stays `not-equal`) |
| `plus-assign` `minus-assign` `multiply-assign` `divide-assign` `modulo-assign` | `+=` `-=` `*=` `/=` `%=`; the parser desugars `x op= e` into `binding x #f (binary op ...)` |
| `assign` `plus` `minus` `multiply` `divide` `modulo` `less` `greater` | `=` `+` `-` `*` `/` `%` `<` `>` |
| `NL` `EOF` | newline token, end of input |

The parser reads the keyword literals from their kind, not from `value`: `true` → `#t`, `false` → `#f`, `nil` → the symbol `'nil`.

## `src/lexer.rkt`

`(lex input) -> (listof token) | diagnostic`. One pass over the source:

- CRLF normalizes to one newline; a lone carriage return is `LEX-UNEXPECTED-CHAR`.
- `NL` is suppressed inside `()`, `[]`, and `{}`; each LF/CRLF outside them emits one NL, including blank/comment lines.
- A final `NL` is synthesized before `EOF` when the file does not end with one.
- `#` starts a comment that runs to the end of the line.
- A lowercase name may end in `?` or `!` regardless of whitespace before `(`; `!` followed by `=` stays an operator, so `a!=b` is still `a != b`. The parser rejects suffixes on bindings, parameters, and fields. `try` is a keyword.

## `src/ast.rkt`

Every node is `#:transparent` with `span` as the last field.

| Group | Nodes |
| --- | --- |
| declarations | `program`, `import-decl`, `export-decl`, `function-decl`, `param`, `struct-decl`, `enum-decl`, `enum-variant`, `field-decl`, `type-ref` |
| statements | `binding`, `return-stmt`, `loop-control`, `expr-stmt`, `if-branch`, `if-stmt`, `case-stmt`, `case-arm`, `wildcard-pattern`, `literal-pattern`, `variant-pattern`, `while-stmt`, `for-stmt` |
| expressions | `literal`, `type-expression` (name, span; JSON type arguments only), `name-ref`, `call`, `enum-constructor`, `function-ref` (name, span), `invoke` (target, args, span), `named-arg`, `construct`, `list-lit`, `map-lit` (with `map-entry`), `field-access` (target, name, span, mutable `resolved`), `method-call` (target, name, args, span, mutable `resolved`), `typed-target` (expression, type; checker-made receiver), `interpolation` (parts: strings and expressions, span), `inspection` (target, span; checker-made for `x.inspect`), `block-lit` (params, body, span) with `block-param` (name, type or #f, span), `index-access`, `try-expr` (operand, span), `unary`, `binary` |

Design points: one `type-ref` covers `Int`, `List[Int]`, and `List[List[Int]]`; one `literal` covers integers, floats, strings, booleans, and `nil`; grouping `( expr )` produces no node; `call`/`construct` store the name as a string; `unary`/`binary` store the operator as the token-kind symbol (`'plus`, `'and`, `'equal`).

## `src/parser.rkt`

`(parse tokens) -> program | diagnostic`. Recursive descent over the token vector:

- Precedence ladder: or → and → equality → comparison → additive → multiplicative → unary → postfix → primary.
- Arithmetic levels are left-associative; equality and comparison take a single optional operator, so `a < b < c` and `a == b == c` are `PARSE-CHAINED-COMPARISON`, while `a < b == c < d` is valid.
- Top level accepts def/struct/enum/import and export def/struct/enum. `case` uses an optional `do`, `->`, and `end`; `while` and `for` headers also take an optional `do`. A case arm body is either a NL and a block, or one simple statement on the arrow line followed by more statements. A qualified function name without `(` is a `call` with no arguments. as is contextual. Qualified names cover imported types, enum constructors/patterns, calls and function references. Module nodes must pass through modules.rkt before check.
- A statement starting with `name` is a binding when the next token is `=` or `:`; otherwise it is an expression.
- Stray `NL` tokens are skipped at the top level and between statements (see the gotcha in `SKILL.md`).

## `src/modules.rkt`

`(load-program path)` links imports before `check`. The std-only guard lives in its name resolution: a two-part name whose module is in `std-only-modules` (`src/builtins.rkt`, today `HttpWire`) and that no import alias names is `CHECK-UNKNOWN-NAME`, with a help that shows `import "std/http" as HTTP`, unless the module was embedded from `stdlib/` (the `std/` sources of `src/stdlib.rkt`). A user file, a relative import and a `pkg/` module all get it. `HttpWire` is also left out of `help`, its JSON and every "did you mean" (`public-builtin-names`).

## `src/checker.rkt`

`(check program) -> program | diagnostic`. Registration first, then bodies, stopping at the first error:

- Enum names are registered before struct fields resolve; struct names precede field resolution; enum payload templates resolve after all struct names exist; function signatures follow. This allows forward references and generic enum payloads.
- Catalogued builtin function names cannot be redefined. `ok` and `error` are additionally reserved on locals, parameters, loop variables, and fields.
- Types are values, not structs: primitive symbols; builtin type lists such as `(list 'List T)`, `(list 'Map K V)`, `(list 'Result T)`, `(list 'Task R)`; `(list 'Struct NAME)`; nominal enum values `(list 'Enum NAME ARG ...)`; and enum-only type variables `(list 'TypeVar NAME)` during payload registration.
- Builtin module calls keep their dotted name in `call-name`. `check-builtin-call` reads arity/signature/fixed types from `builtins.rkt`; generic rules remain explicit stage-local branches. Lowering reads the same entry's implementation key and trusts checked arity.
- String operations count Unicode characters. Numeric conversions accept signed decimals: non-bang forms return Result; bang failures remain `RUNTIME-INVALID-NUMBER` / `RUNTIME-INTEGER-OVERFLOW`. IO.gets returns Result[String]; IO.gets! retains the old String/EOF diagnostic behavior.
- Expected types must reach builtin calls for contextual ok/error and unwrap/default. An untyped error is CHECK-RESULT-TYPE. `try-expr` requires a Result-returning function and a Result operand; its payload type may differ from the enclosing success type. It does not guarantee a return.
- Scopes are a stack of hashes holding `name -> (cons type immutable?)`. The `for` variable is immutable.
- A plain binding to a visible name is an update and must keep its type; an annotated binding to a visible name is `CHECK-ANNOTATION-ON-EXISTING`; a fresh name that is already visible is `CHECK-SHADOWED-NAME`.
- `check` returns the same `program` when it is valid; lowering trusts it and does not re-check types.
- `(check program #:types table)` also records each checked expression node's type in the caller's mutable `eq?` hash (one `hash-set!` in `check-expression`). The literal 2^63 under unary minus is never recorded; `lower.rkt` handles it by rule.

## `src/lower.rkt`

`(lower program types) -> ir-program | diagnostic`. One `ir-function` per `function-decl` (index order = declaration order, `entry` = `main`). Slots: parameters first, then locals, which are resolved statically and freed when their scope ends, then temporaries with a stack discipline so a call window is always the highest live slots. A new local is lowered straight into its slot; an assignment to an existing local goes through a temporary and `move`. Unsupported forms or types are `LOWER-UNSUPPORTED` at the node span; a Racket exception becomes `LOWER-INTERNAL` at the program span. A `method-call` or `field-access` with `resolved` set lowers its resolved node without a step and checks the outer node's type, because the synthetic call that `check-method` builds is not in the types table; a `typed-target` lowers its expression and checks its recorded type. `format-ir` is the `--dump-ir` text.
Builtin records the VM knows (`builtin-structs`: `FileInfo`, `Header`, `HttpResponse`, `HttpClientOptions`, `ProcessOutput`, fields in record order) are appended to the program's structs when a checked type mentions them, with the records they need (`HttpResponse` needs `Header`); the C side finds them by name (`agc_builtin_struct`).

## `src/bytecode.rkt`

`(ir->bytecode ir) -> bc-program | diagnostic` resolves labels, merges adjacent `step`s (split above 65535), and builds the constant pool, builtin imports `(name . arity)` and the span table (span 0 is the program span; multi-span instructions use consecutive entries). `(write-bytecode bc) -> bytes | diagnostic` gives the `.agcb` bytes of `docs/vm/03-ir-and-bytecode.md` 4.6; there is no Racket reader, the C loader is the only one. `BYTECODE-LIMIT` when a function needs more than 65535 registers; both functions turn a Racket exception into `BYTECODE-INTERNAL` at the program span.

## `src/builtins.rkt`

One catalog of name, parameters, result, generic rule tag, implementation key, effects, and description. `std-only-modules` (`HttpWire`) lists modules only `stdlib/` may call (`std-only-name?`; `public-builtin-names` leaves them out for help and suggestions). `builtin-ref`, `builtin-signature`, and `builtin->jsexpr` serve checker/lowering/help. Shared `type->string` and `did-you-mean` keep help and checking consistent. Effects are informational only, except that a builtin with no effects whose result is unused is `CHECK-UNUSED-VALUE`: the `Test` assertions carry the effect `test` so they may stand as statements. `Test.eq` uses the rule `test-eq`: both arguments have one type that passes `data-type?` (the types with `to_s`, which are the §25.4 equality set plus `Json`); `TestCase` is in `opaque-types` and `Test` is a reserved name. Every entry's implementation key must be in `vm-builtins` (`tests/bytecode-test.rkt`) and run in a golden fixture; do not add test-only exports.

`builtin` has an automatic alternatives field, filled only during catalog initialization. `builtin-ref` optionally selects a signature by arity; checker and lowering use the same selection. Map.get/2 returns Result[V]; Map.get/3 returns V with an eagerly evaluated default. Text help lists both signatures, and its JSON help carries overloads; single-signature JSON output is unchanged. List.repeat count errors are RUNTIME-INVALID-COUNT at the argument span, with a 1048576-element cap. List.set reuses RUNTIME-INDEX-OUT-OF-RANGE. Map.delete removes both hash storage and insertion-order keys.

## `src/main.rkt`

`test` parses its own options (paths, at most one --steps, at most one --only TEXT, --allow-run, --seed, --ai/--json; no paths means the defaults, chosen by the driver) and calls `run-agentica-test` in `src/bdd-driver.rkt`, then prints the text it returns and exits with its code. BDD options after test are parsed separately so ordinary program arguments remain untouched.

Reads the file (a missing file prints one plain line and exits 2), builds a `source`, and calls `lex`, `parse`, `link-program`, `check` and `lower`, then runs the bytecode on the VM. A diagnostic is printed by `format-diagnostic` (header, message, source line, caret run) on stderr with exit 1. `--dump` pretty-prints the checked tree instead of running it; `--dump-ir` prints `format-ir` of the lowered program. `compile FILE -o OUT` (first argument only, exactly that shape, else usage exit 2) checks, lowers and writes bytecode, and it cannot be combined with `--dump` or `--dump-ir` (usage, exit 2); the `#:types` table is built only for `compile` and `--dump-ir`; lowering diagnostics exit 1, an unwritable output prints one line and exits 2. Arguments after the source file reach the VM as `System.args`, and the driver exits with the VM's code. No source file exits 2. `check` never runs; --ai/--json use the same structured diagnostic. `help NAME --json` reads the catalog without a source file (unknown target exits 2). Help and test handle trailing style options; options on other commands precede the command/file so program args stay intact. --max-steps accepts a positive integer and reaches only the VM. --allow-run enables Process.spawn and, for `test`, reaches step handlers and programs under test; check and help need no flag.

## BDD (`agentica test`)

`agentica test` runs on the VM and is written in Agentica (phase 21, `docs/future/31-bdd-in-agentica.md`, user docs in `docs/bdd.md`). `std/bdd` is the public step API; `std/bdd/gherkin` and `std/bdd/match` (Gherkin parsing and step matching) and `std/test/runner` and `std/test/report` (the runner and report, shared by BDD and unit tests) are internal (importable through `std/` like any registered module, but not in the programming skill or the site). All are registered in `src/stdlib.rkt`.

- `src/bdd-driver.rkt` (`run-agentica-test paths step-files #:style #:allow-run #:seed #:vm`, returns `(values code text)`): makes a private 0700 temp dir `agentica-bdd-new-<hex>` and reads the user's uid and gid from it (no FFI), refuses a `TMPDIR` without the sticky bit that others can write to, or that its group can write to unless it has the user's uid and gid and no setgid bit (the user-private-group case), locks the dir's `lock` file exclusively for the whole run, then renames the dir to `agentica-bdd-<other hex>`, a second random value, so the sweep never sees an unlocked new dir (then removes such dirs of the same user whose `lock` it can take, left by a killed driver; links and dirs without `lock` are left alone; any Racket exception becomes an INFRA report), compiles the step program (or a default `BDD.run([])` one) and a tiny root that calls `Runner.main()` into 0600 `.agcb` files, discovers the feature files, writes `config.jsonl`, and runs the runner VM with `--allow-run [--seed N] --driver-pid PID -- runner.agcb config.jsonl`, without the metrics variables (`--driver-pid` ties the runner to the driver with `PR_SET_PDEATHSIG`; the runner's bytecode is its one-shot input). Discovery lives here, not in the runner, because `File.stat` follows links: `file-or-directory-type` sees links, folder links are skipped, and an unreadable folder, an unreadable entry, a broken `.feature` link or a non-UTF-8 folder or `.feature` name is a `RUNTIME-BDD-INFRA` entry for that path. `config.jsonl` is the config on its first line (VM, step bytecode and source path, `steps_error`: the step program's front-end diagnostic as `--json` writes it, so the report stays in Agentica; the Agentica command for programs under test, `count`, `empty_path`, style, allow_run, seed), then `count` lines of `{path, problem}`; the runner reads them with `File.read_line` in a `map` over `0...count`. A runner exit of 0, 1 or 2 with an empty stderr is the answer; anything else, an exception, a missing VM, or more than one `--steps` is a one-file `RUNTIME-BDD-INFRA` or `USAGE` report built in Racket. The dir's entries other than `lock` are removed first, then `lock` and the dir, then the lock is closed, ignoring failures (a leftover dir keeps its `lock`, so it is swept later); the sweep removes dirs in the same order. This runs in a `dynamic-wind` post wrapped in `(with-handlers ([exn:break? raise]) ...)`, since Racket skips posts on an uncaught break in the main module; the runner is stopped with `stop-vm` (`src/vm-launch.rkt`).
- Unit tests (25b): `src/bdd-driver.rkt` (`run-agentica-test ... #:only #:test-timeout-ms`, defaults `""` and 30000; tests pass a short deadline here) discovers `*_test.agc` next to `.feature` files in the same walk (an entry's `kind` is `tests`, `feature` or `""`), uses `specs/` and `test/` when no path is given (a missing default folder is skipped; nothing found is `CHECK-BDD-EMPTY`), and compiles each test file into `test-<n>.agcb` (a front-end diagnostic goes to the entry's `front_end` as `--json` writes it); the config gains `only` and `test_timeout_ms`. In the runner, the seed is `--seed` or one drawn with `Random.int` and passed to every child (`--seed` always) and to the report. The steps are listed only when there is a feature; a broken step program is one `steps` file error, and the test files still run. `stdlib/test/units.agc` (`std/test/units`) runs a test file: a list child (`--agentica-test list`, the token line, then `Process.output`; a `fail` record, a missing `ready` or a non-zero exit is a file error, a file whose `main` never calls `Test.run` is `RUNTIME-TEST-RUN`), the `--only` filter, then one run child (`--max-steps` 1,000,000 × (tests + 1)) that gets the token and one index per test; a record counts only at the start of a line and with the token; other lines are the test's output (1 MiB from the index, `RUNTIME-BDD-OUTPUT-LIMIT`; kept in a `Map[Int, String]` so it costs O(n log n), and the last 64 Ki characters go to `output` for a failed test). The deadline is `test_timeout_ms` from the index (`RUNTIME-TEST-TIMEOUT`); a timeout, an end of stdout (the child's last stderr diagnostic, else `RUNTIME-BDD-PREMATURE-EXIT`, plus the stderr lines the program wrote itself in `output`) or the output limit stops the child, and the remaining tests are `Verdict.NotExecuted`. After the last test it closes stdin and waits: exit 1 with the unobserved summary is a `RUNTIME-TASK-CRASHED` file error. `stdlib/test/child.agc` (`std/test/child`) holds what both runners share: the marker, record fields, `left`, `located`, `stderr_diagnostic` (which also reads the unobserved summary) and `stderr_text`. Tests: `tests/unit-test-test.rkt` with `tests/fixtures/unit/` (outcomes, captured output, exit, timeout, names, `--only`, the seed, a mixed folder, the default `test/`) and the `std/` unit tests in `tests/std/`.
- `stdlib/test/runner.agc` (`std/test/runner`; it imports `std/bdd/gherkin` and `std/bdd/match`): reads the config, lists the steps with one captured child (`--agentica-bdd list`, read once with `Process.output`), compiles the patterns, reads each listed `.feature` file (over 1 MiB is a `RUNTIME-BDD-IO` file error), parses and resolves each scenario, and runs every scenario that resolves in its own child VM (`--agentica-bdd scenario`, `--max-steps` 1,000,000 per step plus one, a 30 s scenario deadline), then prints `Report.json` or `Report.text` and exits with `Report.exit_code`. It talks to the child over stdin/stdout: an init line, then one step line per step; the child answers with records, lines that start with U+001E and `agentica-bdd ` and carry JSON (`assert`, `step`, `fail`, `end`, `ready`). Other output, and a marked line whose record does not parse, counts toward the 1 MiB per-step limit. An `end` whose `index` is not the current step is a `RUNTIME-BDD-INFRA` protocol error; a failed `Process.send` of a line fails the step at once (`send exceeds` is `RUNTIME-BDD-IO`, anything else goes through `read_failure`); a `fail` record after the last step is the scenario's error. A child that dies prints its diagnostic on stderr with `--json`; the runner reads the last line with `Report.from_json`, else `PREMATURE-EXIT`.
- `stdlib/bdd.agc` (`std/bdd`): `step`, `run`, the `Context` value passed through each handler (scenario state, the step's doc string or table, the program under test), `assert`, `set`/`get` and the program steps. The `then_*` checks compare with `Test.eq` (`agc_equal`; a `Json` line by its canonical text) and put the inspect texts of expected and actual in the `fail` record (`Json` as `JSON.encode`, the same text `agc_test_text` gives), so BDD and unit tests show values the same way. `run` puts the 12 predefined steps first; in the child it checks the step index and pattern, calls the handler, then fails on pending tasks (`Task.pending_count`) and on an unobserved task crash (`Task.unobserved_crash`), probes the program's output limit and writes `end`. Every failure writes one `fail` record and exits 1.
- Runtime codes: `RUNTIME-BDD-CONTEXT`, `ASSERTION`, `NO-ASSERTION`, `PREMATURE-EXIT`, `PENDING-TASKS`, `DUPLICATE`, `PATTERN`, `TIMEOUT`, `OUTPUT-LIMIT`, `PROGRAM`, `JSON`, `IO`, `INFRA` and `USAGE` with the same prefix; resolution uses `CHECK-BDD-UNDEFINED`, `AMBIGUOUS` and `EMPTY`; the feature parser `PARSE-GHERKIN-*`. Tests: `tests/bdd-test.rkt` (the step program, isolation, registration, usage), `tests/bdd-integration.rkt` (programs under test, limits, seed, cleanup), both through the CLI in-process, the `bdd-*` goldens for `std/bdd/gherkin` and `std/bdd/match`, and the `test-report-*` goldens for `std/test/report`.
- `stdlib/bdd/gherkin.agc` (`std/bdd/gherkin`, 21c) parses the English Gherkin subset with stable codes, the first error and spans. `parse(file, text)` returns `Outcome.Done(Feature)` or `Outcome.Failed(Diagnostic)` (code, message, `Span`, the `std/test/report` type); a `Span` is file, line, column 1 and the end column of the raw line, with no offset. A step's `argument` is `NoArgument`, `DocString` or `DataTable`; a scenario's `example` is the report's `Example`: `NoExample` or the Examples `Row` span; kinds are the strings `Given`, `When` and `Then`. Table rows and `<name>` substitution split the text and join it once, with no `+=` or `push` per character or cell, so they cost linear time in the line. Building the step, row, Examples, draft and scenario lists with `push` per line is still quadratic in the line count; it will be optimized later. Goldens: `bdd-gherkin-outline`, `-sections` and `-arguments` (every case of the deleted `tests/gherkin-test.rkt`).
- `stdlib/bdd/match.agc` (`std/bdd/match`, 21d) compiles and matches step patterns and runs the duplicate and resolve checks, by hand with no regular expressions; it imports `gherkin` for `Diagnostic`, `Outcome` and `Step`, and `std/test/report` for `Span`. `compile(texts, where)` returns `Outcome.Done(List[Pattern])` or the first problem in order: a text seen before is `RUNTIME-BDD-DUPLICATE`, a bad one `RUNTIME-BDD-PATTERN` (the reason, then `: ` and the pattern), both at `where`, the span the caller gives (the step program's first line). A `Pattern` is its `text`, the `head` literal and one `Slot` (an `{int}` or `{string}` capture, then a literal) per placeholder, split on `{` with `List.map`. `captures(pattern, text)` is `ok(List[String])` or `error("no match")`: a whole-text match that backtracks like the old regular expression (`{int}` from the longest digit run down, `{string}` up to the first unescaped closing quote, each `\X` decoded to `X`). `resolve(patterns, step)` matches every pattern and returns `Resolved(index, captures)`, or `CHECK-BDD-UNDEFINED` or `CHECK-BDD-AMBIGUOUS` at the step's span (the report's `actual` is the step text, added by the caller). Goldens: `bdd-match-captures`, `-resolve` and `-errors` (the matching cases and the predefined patterns); `json-canonical` pins the JSON rule that `Test.eq` on `Json`, and so `then_json_line`, relies on (`JSON.encode(JSON.parse(x))` sorts keys and keeps the last duplicate, `sort_members` in `vm/json.c`).
- `stdlib/test/report.agc` (`std/test/report`, 21e; moved from `std/bdd/report` in 25b) builds the report and imports nothing: it owns `Span` (file, line, column, end column) and `Example` (`NoExample` or the Examples `Row(Span)`), which `std/bdd/gherkin` and `std/bdd/match` import from it. Its input is the run as data, which the runner fills: a list of `FileResult` (path, feature, scenarios, `verdict`), each `ScenarioResult` with name, tags, location `Span`, `example`, `duration_ms`, steps and `verdict`, each `StepResult` with text, location and a `StepStatus` (`Passed`, `Failed(Error)` or `NotExecuted`). A `Verdict` is `Pass` or `Fail(Error)`: a file's own error (parse error, step program), or a scenario's first failure. An `Error` is the diagnostic as the VM's `--json` writes it: code, message, the `Span` plus `end_line`, `expected` and `actual` as `Detail` (`Unknown` or `Known(String)`), and `original`, `JSON.null()` or the whole object `from_json` parsed; `from_json(text)` reads a diagnostic as `--json` writes it (a front-end error of the step program) and keeps that object, so the report writes every key unchanged (`help`, `function`, `callee`, `labels`), `error_at(code, message, span)` builds one from fields (the runner turns a `Gherkin.Diagnostic` into one with it), `with_actual` adds the text it is given as `actual` (the runner passes the step text's inspect form, `step.text.inspect`) to an undefined or ambiguous step (an error built from fields; it returns an error with a non-null `original` unchanged), `file_error(path, kind, error)` builds a file entry. `json(files, seed)` builds the report with `JSON.object` (keys come out sorted, the canonical form; the statuses, totals, `ok` and `not_executed` are derived, not passed in; a file has `kind`, a scenario `output`; a `Verdict` can be `NotExecuted`, a test that never ran), `text(files, ai, seed)` is the plain or `--ai` text (a test file's lines name its path where a feature name goes, `SKIP` for a test not run, a failed test's output indented below it or after ` | output`, and `, seed N` on the last line when the exit code is not 0) without the final newline (`expected` and `actual` as they are: a BDD or `Test` assertion already wrote them in the inspect form, once, so the report does not quote them again), and `exit_code(files)` is 0 when at least one scenario ran and nothing failed, 2 when a file or scenario error is `RUNTIME-BDD-INFRA` or `RUNTIME-BDD-USAGE`, else 1. Every list is built with `List.map` and joined once, so a report costs linear time. Goldens: `test-report-run` (a run parsed and resolved by the other two modules: passed, failed and not-executed steps, an assertion with expected and actual, undefined and ambiguous steps with `actual`, Examples rows, file errors) and `test-report-exit` (the exit-code rules with a usage error, a front-end error with help, function and labels, escapes in the text, a range over several lines). `original` must only come from `from_json`: any other error keeps `JSON.null()` there, or `json` would write the stale object instead of its fields.
