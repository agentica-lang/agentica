# Front-end recipes and Racket gotchas

Step lists for common front-end changes (keyword, AST node, syntax, diagnostic, stage, tests), the Racket and lexer gotchas of this repo, and how to read a failure. Read before editing `src/*.rkt` or `compiler/`.

## The freeze and the Agentica front end

Roadmap row 7.2.7 froze the Racket front end. By default, from then on `src/` takes no new syntax and no new checker rules. Its only changes are bug fixes and the data that row 7.2.7 lists: builtin table rows in `src/builtins.rkt` with their `vm-builtins` names in `src/lower.rkt`, builtin record and enum entries, registry lines, std-only and reserved names, and message texts. Every later language change goes into `compiler/` (`docs/future/35-self-hosting.md`), and the recipes below that add a keyword, a node or a syntax form describe the change to make there once its stage is ported. A bug fix in a ported stage changes `src/` and `compiler/` in the same PR, with a golden case for it. They may be relaxed when following them costs more than it saves; the PR says which rule it relaxes and why. `CHECK-DECL-ORDER` (the fixed declaration order of a file, in `src/modules.rkt`) is such a relaxation: a small style rule the owner asked for; the linker port carries it (`declarations.agc`) and the checker port keeps it (`check_register.agc` and `declarations.agc`). So is `value.with(...)` (15c): a syntax form in both parsers, the checker rules, a privacy predicate in the linker and the `STRUCT_WITH` opcode, on the owner's decision of 2026-10-15 because `compiler/` uses immutable struct updates; the checker and modules ports carry it. So are the import forms of 44a0-1 (roadmap row 7.2.8, owner decision of 2026-10-15): `import Alias from "path"` and `import {a, B as C} from "path"` in both parsers (`import-decl` has `alias` and `names`) and both linkers (the `named` table, the collision, `CHECK-IMPORT-NAME` and `CHECK-IMPORT-RENAME` checks, bare names rewritten to linked names, the `.with` privacy set); the path-first form of earlier versions was removed in 44a0-2 (`PARSE-UNEXPECTED-TOKEN` at the string, with the help `write import Alias from "path"`). The checker never sees an import (named imports are rewritten to linked names before it). So are the module constants of 44a2 (roadmap row 7.2.8, owner decision of 2026-10-15), in the paragraph "Module constants in the front ends" below. So is `CHECK-TOO-DEEP` (step 4): both checkers stop at 1,000 levels of expressions and statements, because the parser limit does not bound the depth of the tree and the Agentica checker recurses on it within the VM call limit of 10,000; with it, a fix for a Racket exception on two different generic enums in `unify-type!`.

`compiler/` holds the Agentica front end, one stage per PR in the order of 35.4. So far it has the lexer, the parser, the module linker, the checker and the lowering: `source.agc`, `token.agc` and `diagnostic.agc` (the data of `src/source.rkt`, `token.rkt`, `diagnostic.rkt`), `lexer.agc` (`src/lexer.rkt`), `unicode.agc` with the generated `unicode_table.agc` (Racket's `char-graphic?` for the text of `LEX-UNEXPECTED-CHAR`), and the entry `lex.agc` with `lex_text.agc`. Every entry and the module loader read a file through `source_file.agc` (`src/source-file.rkt` on the Racket side): strict UTF-8, no size limit, and `LEX-INVALID-UTF8` at the first bad byte (35.4). The parser is `ast.agc` (`src/ast.rkt`), `parse_base.agc` and `parser.agc` (`src/parser.rkt`), with the entry `parse.agc` and `parse_text.agc`; `text.agc` holds the quoting and span printing both text forms share. The linker is described after the parser below. In a `compiler/` file the order is: imports and module doc, structs and enums, exported functions, private functions (declaration order does not matter in Agentica, so the order is only for the reader). Code follows 35.5: build lists with `push` and strings with `join`, and use loops, not recursion over the input. `lexer.agc` is a `while` over the index with a `case` on the character class and mutable locals, calling small `scan_*` functions that return a token (or a `Diag.Outcome` of one), and `lex` moves to the token's end. Character classes, name and number characters, string stops, keywords and block openers are Set and Map lookups built once in `new_input`: they are about 2.5 times faster than a chain of predicate calls, and calls cost more than assignments on the VM, so measure before changing the style of a hot function (a tail-recursive `step(state)` form with `state.with(...)` was measured and was about 3-6% slower). The measured costs are in `.agents/skills/agentica-programming/references/performance.md`; functions of about 60 lines or fewer are the target (the `while` in `lex` is 78 lines). Positions and offsets count characters, as in Racket.

The lexer's output has a text form, one line per token (`kind start-end "lexeme" value`, spans as `offset:line:column`, `=` when the value is the lexeme) or one `ERROR` line. The Racket printer is `tests/frontend-lexer-common.rkt`; `compiler/lex.agc` prints the same for each file in `System.args()`, after a `== path` line. Token kinds are Strings in `compiler/`; they must match the symbols of the kind list in `src/token.rkt` and `references/stages.md`, because the parser compares them. Goldens are in `tests/fixtures/frontend/lexer/` (`NAME.input` and `NAME.tokens`); `.input` files keep their bytes (`-text` in `.gitattributes`). They hold the message and help text on purpose: 35.2 keeps the texts equal, an exception to "tests assert codes, not messages". They are not tied to live files, so they still work after Racket is deleted. While Racket exists, `tests/frontend-lexer-test.rkt` also compares the two lexers live on `examples/`, `stdlib/`, `tests/fixtures/vm/` and 300 generated inputs (the cases named "while Racket exists"; delete them with `src/`).

The parser has a text form too: one node per line, two spaces of indent per level, `role: kind #id start-offset:line:column-stop-offset:line:column attrs`, the root as `program #id span`. Spans print as `offset:line:column-offset:line:column`. Attributes are `name="x"`, ` op=plus op-span=SPAN`, ` value=int:N`, `float:bits:N` (signed IEEE bits), `string:"..."`, `bool:true` or `nil`, ` piped=true|false`, ` type-parameters=["T"]`, ` bindings=["a",-]`, ` doc="..."` and ` module-doc="..."`. An `import-decl` prints ` path="x" alias="Mod"`, or ` path="x" names=[...]` with each name as `"A"@SPAN` and a rename as `"A"@SPAN as "B"@SPAN`. The else part of an `if` is a line `else:`, and text parts of a string interpolation are `part: text "..."`. A failure prints the lexer's `ERROR CODE SPAN "message" "help"|-` line (a `LEX-` error passes through). The Racket printer is `tests/frontend-parser-common.rkt` (not `src/`, so `--dump` is unchanged); `compiler/parse.agc` prints the same for each file argument.

Node ids are dense, start at 0 and follow post-order: a child has a smaller id than its parent, siblings count in source order, and the `program` node has the last id. The Agentica parser builds trees bottom-up, so it gives ids as it goes; the Racket printer numbers by a post-order walk. Docs are a `doc` field on the declaration, field, variant and export nodes and `module_doc` on `Program`, where Racket keeps a span table. Ids restart per call: `Parser.parse(tokens, first_id)` numbers from `first_id`, and `Ast.next_free_id(program)` is the first id for the next file, so the modules of step 3 can share one numbering (`compiler/parse.agc --first-id=N` and `--continue`, and `parser-text #:first-id`, test it).

Parser goldens are in `tests/fixtures/frontend/parser/` (`NAME.input` and `NAME.ast`): valid files for every node kind, one `err-*` file per `PARSE-` diagnostic site of `tests/parser-test.rkt`, and `deep-*` files for the nesting limit. Both parsers stop with `PARSE-TOO-DEEP` when the nesting passes 1,000 levels (counted in `parse-statement`, `parse-expression`, each prefix operator, `parse-type`, and each link of a chain, where what follows the k-th link starts k levels deeper); this is a new parser rule in `src/`, allowed because the Agentica parser needs a bound well inside the VM's call depth (10,000 frames, up to about 8 frames per level; equality and comparison add no level but cost frames, so the tightest shape, calls with comparisons inside, overflows at 1.25 times the limit; the parser's stack is not shared with later passes). It bounds the parser's calls, not the depth of the tree (see `references/stages.md`). The Agentica parser takes `(env, pos, ids)` and returns a `Result` with the new position and the next id; a failure is a packed diagnostic in the `Result` error, so `try` stops at the first error.

The module linker (step 3) is `modules.agc` (the loader: it walks the imports with an explicit stack in the order of `src/modules.rkt`, so ids and the first failure agree), `resolve_import.agc` and `import_path.agc` (`std/`, `pkg/` and relative resolution, the import path rules), `resolve.agc` and `rewrite.agc` (the linked name of every name), `linker.agc` (`Linker.link_file`, `Linker.program`), with `declarations.agc` (also `CHECK-DECL-ORDER`), `suggest.agc` (the "did you mean" help), `link_env.agc` (`Env` and `Settings`: the `stdlib/` folder and the environment variables, passed in, never read inside) and `link_failure.agc` (a failure is a packed diagnostic with its file, because a `Span` has no file). The name tables it needs (reserved type names, bare builtins, builtin enums, std-only modules) come from the builtin catalog, described below. Names imported by name are the `named` table of a `Module` (local name to a `Named`: the module key and the original name). `modules.agc` fills it when the file the import names has finished loading, because the checks need its exports and `src/modules.rkt` runs them after `visit`: the frame keeps the key of that file in `pending`, and the next step binds the names (`bind_names`) before the frame goes on to its next import. `Resolve.resolve` and `Rewrite` read the table, `Linker.visible_structs` adds the files of the table to the `.with` privacy set, `Declarations.import_line` renders the import line for the `CHECK-IMPORT-PATH` helps, and `Suggest.unknown_import_help` is the help of `CHECK-IMPORT-NAME` for both `Alias.name` and an imported name. The loader and the rewrite use no mutable state: a `Walk` struct (updated with `.with`) goes through a tail-recursive loop, and the rewrite recurses on the tree (about one VM call per level, so trees deeper than about 9,900 levels overflow; `docs/future/35-self-hosting.md`, 35.9).

Module constants (44a2-1; §44) are a declaration node `const-decl` (`name`, optional `type`, `value`, `exported`, `span`; `Decl.Constant(ConstDecl)` in `ast.agc`) and a read node `const-ref` (`name`, `span`; `Expr.ConstRef`) that only the linker makes. The parser reads a constant at the top level when a `TYPE_NAME` is followed by `=` or `:` (`constant-start-at?`, `constant_start?`), raises `PARSE-CONSTANT-NAME` for a name that is not `UPPER_SNAKE_CASE` (`constant-name?`, `constant_name?`) and lets a constant follow another constant, after `export` or a doc block, with no blank line. `NAME.x` and `NAME.x(...)` parse as module calls; `NAME.with(...)` is read as a struct update on the name. The linker (`rewrite.agc`, `rewrite` in `modules.rkt`) makes the receiver `const-ref` and the node a `field-access` when the call had no parentheses and no arguments (a block counts as an argument), otherwise a `method-call`; the Racket parser keeps the parenthesized bit in a weak table that `parenthesized-call?` exports. `Mod.NAME` on a constant is `CHECK-IMPORT-NAME`; an unknown name in capitals (a `type-expression` that no declaration, import, alias or reserved type owns) is `CHECK-UNKNOWN-NAME` from the linker, with a did-you-mean over the constants the file can read (`visible-constants`, `Resolve.unknown_constant?`), because only the linker knows the local names of named imports; the parser reads `NAME.with(field: x)` as a struct update only when `field:` follows the parenthesis, so `Alias.with(1)` stays a call; a named import of a constant joins the names of the file (`rename-ok?` wants a constant name for a constant). The new receiver needs a node id of its own: the Agentica linker numbers it `Linked.ids` (twice the parser ids when any module declares a constant) so that the id is the parser total plus the id of the call, and `tests/frontend-modules-common.rkt` numbers the Racket tree the same way from the `#:files` box of `link-program`. The checker reads both trees through one walk (`src/constants.rkt`: `node-children`, `constant-references`, `constant-order`; `compiler/const_walk.agc`) so the order and the cycle span agree; `check_const.agc` (`Constants.check_all`) and `check-constants!` in `src/checker.rkt` run after `main` and before the function bodies. The initialization order is `Checked.constants` in Agentica; in Racket the lowering calls `constant-order` again. The check text ends with `constant-order ["A","B"]` when the program has constants. `src/lower.rkt` lowers the constants (`plan-constants` in `src/constants.rkt`, 44a2-2; `vm-lowering.md` has the layout); `compiler/` has no lowering yet, and step 5 must carry it. Checking a rule with `tests/checker-test.rkt` for a constant goes through `link-program` (`check-linked`), because the checker does not see a bare `NAME` otherwise.

The linked program has a text form too: `program #id span` for the root, then `module "path"` for each file that declares something, with its declarations (no `export`, linked names) one level deeper, in the node text form of the parser with ids that start at 0 inside each file (the numbers of the real, shared numbering are checked by `link.agc --ids`, which lists `module "path" first=N next=N` for every file read, empty ones too). A struct update prints ` visible=[...]`, the privacy rule of `.with` as the sorted names the file may update (`src/` keeps a predicate in the node; `compiler/` keeps data in `StructUpdate.visible`). A failure prints the parser's `ERROR` line with ` file="path"` added. Paths are the stored names of the .agcb (`Paths.stored_name`, `stored-source-names` in `src/source.rkt`): relative to the folder of the root file, with `..` parts for a file above it, `./std/NAME.agc` for a user file under a `std/` folder, or `std/NAME.agc` for a standard module. Racket has no node ids, so `tests/frontend-modules-common.rkt` parses each file again and gives every rewritten node the id and doc of the node at the same place in the original tree. The goldens are fixture folders in `tests/fixtures/frontend/modules/` (`NAME/root.agc`, the files it imports, an optional `NAME/fixture.env` of `AGENTICA_PATH=` and `XDG_DATA_HOME=` lines where `@/` is the fixture folder, an optional `NAME/fixture.links` of `LINK TARGET` lines that the tests make as symbolic links in a copy, because a checkout may not keep links, and `NAME.linked`); the tests run with no `AGENTICA_PATH` and a user data folder that does not exist unless the fixture sets them.

The builtin catalog (step 4a) is data and lookups in Agentica: `types.agc` (the `Type` enum and `to_text`), `builtin_model.agc` (`Builtin`, `Named`, `Record`, `EnumDef`, and the `Rule` enum, the rule symbols of `src/builtins.rkt` in CamelCase), `builtins.agc` (`Catalog`, built once per run with `Map`s and `Set`s so each lookup is one access: `lookup`, `ref` with an arity, `std_only_name?`, `signature`) and `builtins_data.agc`, generated by `tools/gen-builtins-data.rkt` from `src/builtins.rkt`, `src/builtin-types.rkt` and the reserved names of `src/checker.rkt`. A new builtin row, record, enum or reserved name in `src/` means running the tool; the fast test `tests/frontend-catalog-test.rkt` fails until the file is regenerated, then compares the Racket text form with the Agentica one (`compiler/catalog.agc`) on a golden in `tests/fixtures/frontend/catalog/`. A new rule symbol also needs a variant in `Rule` and an arm in `rule_name` or `later_rule_name` of `compiler/catalog_text.agc` (the test fails on a missing one: the text prints `?`). `suggest.agc` has the `did-you-mean` of `src/builtins.rkt`.

The checker (step 4b) is `check_register.agc` (enums, structs, variants, functions and `main`, in the order of `src/checker.rkt`), `check_stmt.agc` (functions, blocks, statements, `case`), `check_expr.agc` (expressions, operators, `CHECK-TOO-DEEP`), `check_call.agc` and `check_method.agc` (calls, enum constructors, struct construction and update, methods and fields), the builtin rules in `check_rules.agc`, `check_list.agc`, `check_collections.agc` and `check_args.agc`, the help texts in `check_help.agc`, `check_names.agc`, `check_flow.agc` and `check_unused.agc`, the state in `check_state.agc`, `check_types.agc` and `check_failure.agc`, and `checker.agc` (`Checker.check(linked, catalog)`: `Checking.Done(Checked)` with the types and resolutions, or `Failed(Problem)`). State is an immutable `Cx` (declarations, catalog, help tables, file texts) and a threaded `St`; names in scope are one persistent `Map` that a scope snapshots and restores, never deleting from it. The cycle between expressions and statements goes through the function field `Cx.expression`. A failure is a packed `Problem` in the `Result` error. `Type.Unknown` is the expected type when there is none. `Checked.types` is a `List[Type]` indexed by node id (a `Map` took 50% longer), and what `src/` keeps in the mutated `resolved` field of a method call or field access is `Checked.resolved` (`Resolved.Self|Text|Inspect|Call`); a builtin method is checked as the call of the builtin with the receiver as an `Ast.Expr.Typed` first argument (made by the checker, never by the parser). `check_tables.agc` is generated by `tools/gen-check-tables.rkt` from the method and help tables of `src/checker.rkt`; a fast test fails when it is out of date. Add a builtin rule: its `Rule` variant in `builtin_model.agc` (a test checks it against the rows), an arm in `check_rule` (`check_rules.agc`) and a fixture that calls it (a fast test fails when a rule has no fixture).

The check has a text form: the linked program of step 3 with ` type=DEBUG-TYPE` at the end of the line of each expression and block (`Types.debug_text`: `List(Int)`, `Struct(@2::Point)`), and ` resolved=self(T)|text(T)|inspect(T)|call("List.map", T)` on a method call or field access that names a builtin (`T` is the receiver's type); a failure is the `ERROR` line with ` expected="..." actual="..." callee="..." signature="..." labels=[SPAN "text", ...]` when present and ` file="path"`. The Racket printer is `tests/frontend-check-common.rkt` (it reads the `types` table and the mutated `resolved` fields of `src/checker.rkt`); `compiler/check.agc` prints the same. Goldens are `NAME.agc` (or a folder with a `root.agc`) and `NAME.checked` in `tests/fixtures/frontend/check/`: one per reachable `CHECK-` code, valid programs, and `rules.agc` for the rules. They hold the message and help text on purpose (35.2). The slow tier compares the two checkers on the cases of `tests/checker-test.rkt` (it exports `current-text-sink` to collect the programs), `examples/`, `tests/fixtures/vm/`, the `std/` modules, `compiler/`, 1,500 mutated programs, trees around the nesting limit and a generated program of 1,000 functions.

Two tiers: the golden checks run in `(module+ test ...)`. The comparisons "while Racket exists" over live files, the 300 generated inputs, the boundary and large-file guards run in `(module+ slow ...)`, which CI runs with `make test-slow`.

The lowering (step 5) is `ir.agc` (the IR as data: `Instr` with an op, integer arguments, an immediate for `const`, a builtin name and the file index of its spans; a label is an `Instr` with the op `label`), `lower_tables.agc` (`VM_BUILTINS`, the operator tables, the builtin structs: constants, a test checks `VM_BUILTINS` against `vm-builtins`), `lower_state.agc` (`Cx` with the `expression` and `block` function fields that break the module cycles, and `Fx`, the function being lowered: code, registers, labels, the block functions made so far), `lower_expr.agc`, `lower_data.agc`, `lower_stmt.agc`, `lower_scan.agc`, `lower_const.agc`, `lower_program.agc`, and `lowering.agc` (`Lowering.lower(linked, checked, catalog)`: `Lowered.Done(Ir.Program)` or `Failed(Problem)`). It follows `src/lower.rkt` function by function; the function table (declared functions, kept constants, `<start>`, then blocks reserved in pre-order), the register discipline and the order the sources are first named must stay the same, because step 6 writes the bytes from this IR. `LOWER-UNSUPPORTED` and `LOWER-INTERNAL` cannot be reached from a checked program, so no fixture ends in a `LOWER-` code (the two error fixtures end in `CHECK-` and `CHECK-IMPORT-IO`). Lowering recurses on the tree with at most 3 VM frames for each level (the scans are loops), about 3,000 of the 10,000 frames at the 1,000 levels of `CHECK-TOO-DEEP`; `lower.agc --burn=N` starts the lowering N calls deeper to prove it. The text form is its own, not `--dump-ir` (it lacks the sources, the full spans and the JSON field types): `program SPAN entry=N globals=N`, `source N "path" chars=N`, `struct sN "Name" [...]`, `enum ...`, then `fnN "name" params=P captures=C slots=S [entry] @ SPAN` with `  LN:` labels and `    op ARGS @ SPAN` instructions (`rN` registers, `fnN`, `sN`, `vN`, `gN`, `LN`; constants as `int:N`, `float:bits:N`, quoted text); a failure is the `ERROR` line with ` file="path"`. `tests/frontend-lower-common.rkt` prints it from `src/lower.rkt`. Goldens are in `tests/fixtures/frontend/lower/` (`NAME.agc` or a folder with `root.agc`, and `NAME.ir`: 26 programs, one for each lowering path and every opcode, and two that end in an ERROR line (a check failure and an import failure)). The fast tier runs the goldens and `examples/`; the slow tier runs `tests/fixtures/vm/`, the `checker-test` programs, the `std/` modules, `compiler/`, the deep shapes and a generated program.

To add a case, put `NAME.input` in the folder and run `racket tests/frontend-lexer-common.rkt` (or `frontend-parser-common.rkt`). A change to a ported stage reruns the test for that stage; review the golden diff.

## Common tasks

By default, under the freeze, these recipes name `src/` files. New syntax and new checker rules go into `compiler/` instead, and cannot start until the stage they change is ported (the parser for a syntax form, the checker for a rule): they wait (the same default). Only the lexer, the parser and the linker are ported so far, so a new syntax form now goes into `compiler/parser.agc` and `compiler/ast.agc` with a parser golden.

### Add a keyword or operator

1. Add it to the `keywords` hash (reserved words) or the operator hash in `src/lexer.rkt`.
2. If the parser must act on it, add the kind to the relevant `case`/`memq` in `src/parser.rkt`.
3. Add a test in `tests/lexer-test.rkt` (kinds) and, when it affects syntax, `tests/parser-test.rkt`.
4. Run `make test TESTS="tests/<stage>-test.rkt"`.

### Add an AST node

1. Add a `#:transparent` struct in `src/ast.rkt` with `span` as the last field, and add `(struct-out <node>)` to `provide`.
2. Construct it in `src/parser.rkt` and set the span from the first token to the last consumed token (the existing `span-from` helper).
3. Test the node's fields and its span line/column.

### Add syntax

1. Add tokens first if the syntax needs them.
2. Add the AST node if no existing node fits.
3. Write a parse function and call it from the right place: `parse-statement` for statements, `parse-primary` for expressions, `parse-program` for declarations.
4. Add one valid test and one rejection test asserting the diagnostic code.
5. Run `make test TESTS="tests/<stage>-test.rkt"` and the affected example.

### Add a diagnostic code

1. Choose the stage prefix: `LEX-`, `PARSE-`, later `CHECK-` or `RUNTIME-`.
2. Raise it with the stage's `bail`/`fail` helper and a token or position span.
3. Test both the code and the location (`source-position-line`/`-column` of the diagnostic span), as `tests/parser-test.rkt` does.

### Add a pipeline stage

1. Create `src/<stage>.rkt` with one entry point and a `provide`.
2. Require the previous stage's data modules only; do not reach back into the CLI.
3. Wire it into `src/main.rkt` after the previous stage, behind a `diagnostic?` guard.
4. Add `tests/<stage>-test.rkt`. `make test` discovers it automatically; CI needs no change.

### Add tests

- Use `#lang racket`, `rackunit`, and `module+ test` with `test-case` blocks.
- Require sources with relative paths (`"../src/lexer.rkt"`); they resolve from the test file.
- Keep the small helpers pattern from `tests/parser-test.rkt`: `parse-ok` fails loudly when a valid input returns a diagnostic, and `parse-code` returns the code or fails when invalid input parses.
- Cover the happy path, the error path, and the specific behavior the change introduces.

## Racket gotchas

- `define` is not allowed in an expression context, and `(begin ...)` is an expression. `(begin (define x 1) ...)` fails with `define: not allowed in an expression context`. Use `(let () ...)` to open a body that allows internal defines. `cond`/`case` clause bodies, `let/ec` bodies, and lambda bodies already allow them.
- `define` binds like `letrec`. A local named the same as the accessor it calls, such as `(define param-type (param-type x))`, fails with `undefined; cannot use before initialization`. Name locals distinctly.
- `source` is opaque (no `#:transparent`), so printing a tree shows `#<source>` instead of repeating the file text; every other struct is `#:transparent`. Keep any struct that holds the whole source text opaque.
- The lexer and parser are single mutable-pass scanners driven by `set!`. The parser cursor is capped at the last token (`EOF`), so `advance!` never runs past the end and `current`/`peek-token` stay safe at EOF.
- Early exit uses `let/ec` with a `bail`/`return` helper that escapes with a `diagnostic`. This is how a stage stops at the first error.
- `provide (struct-out name)` exports the constructor, predicate, and accessors in one line.
- `#lang racket` provides `pretty-print`; `src/main.rkt` uses it for `--dump`.
- `unary` and `binary` carry `op-span` (the operator token) beside `span`. Operator diagnostics use `op-span`; `node-span` in `ast.rkt` returns any node's span.
- Racket `equal?` treats `+nan.0` as equal to itself and `0.0` unequal to `-0.0`; compare numbers with `=` so `==` follows IEEE 754.
- Positions count Racket string characters, line and column are 1-based, and span ends are exclusive. Keep that convention in new spans.

## Lexer gotcha: stray NL tokens

The lexer emits one `NL` per LF/CRLF outside `()`, `[]`, and `{}`, including every blank/comment line, so extra lines between statements can leave more than one `NL` token. The grammar's `program` and `block` rules do not model this. The parser therefore skips stray `NL` at the top level and between statements. Keep that skip when adding statement forms, or valid files with comments between statements will fail to parse.

Top-level declarations need a blank line after their `end` (`PARSE-MISSING-BLANK-LINE`, checked in `parse-program` from the NL tokens). A `##` doc block is one `DOC` token followed by the `NL` of its last line, and it does not count as a blank line: the check also fires when the next token is a `DOC`. A blank line and a `#` comment line both give one `NL`, so a `DOC` token carries what follows it (`doc-block-next`) for the module-doc rule. The rule only fires when the next token starts a declaration or import, so stray text after `end` stays `PARSE-TOP-LEVEL-STATEMENT`. Inline test programs end each top-level `end` with `end\n\n`, so fragments can be joined safely.

## Error handling

- `make test TESTS="tests/<stage>-test.rkt"` failure: read the failing `test-case` name and the message from the `parse-ok`/`parse-code` helper. A `parse-ok` failure prints the diagnostic the stage returned.
- Smoke test exits 1: `main.rkt` printed `file:line:column error[CODE]`, the message, and a source excerpt with a caret on stderr. That is a stage diagnostic, not a crash.
- A Racket traceback instead of a diagnostic means a stage raised or indexed out of range. Find the token or index and turn it into a `bail`/`fail`; the roadmap requires Agentica diagnostics, never host tracebacks.
- A stage unexpectedly returns a diagnostic: check the first-error rule and that `main.rkt` guards with `diagnostic?` before passing data to the next stage.

## Comments

- `compiler/*.agc`: a `#` comment where the code is complex or copies a Racket behavior on purpose (name the behavior, such as the span or NL rule). Each exported `def`, `struct` and `enum` you add or touch gets a `##` doc block, as in `stdlib/queue.agc` (`compiler/` has none yet; do not add docs to code you do not touch); the file's first doc block, followed by a blank line, is its module doc (`docs/grammar/05-syntax.md`). A `#` comment goes inside the body or above the `##` block, never between the block and its `def` (that is `PARSE-DETACHED-DOC`).
- `src/*.rkt` and `tests/*.rkt`: a `;` comment for the non-obvious why, such as a Racket quirk, a freeze exception or a golden that must not change. Never narrate the code.

## Code style

- Lines in `compiler/*.agc` are at most 119 characters, comments included (`compiler/agentica.toml`, `[style]`), checked by `tests/test_style_line_width.py`. Break a call or list one item per line with a trailing comma, wrap a long expression in parentheses, and flow a doc block over several `##` lines (a generated file comes out of its tool at that width: `tools/agc-format.rkt`).
- Build strings with interpolation, not `+` and `.to_s`. Wrap a long one into a few sentence-sized pieces joined with `+`, never one piece per line.
