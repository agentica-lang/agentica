# Agentica

Interpreter for the Agentica language, written in Racket. The language is defined in `docs/grammar.md`; planned syntax lives in `docs/future.md`; the phased plan and the checklist of what is done live in `docs/roadmap.md`; the bytecode VM design (phase 7) is `docs/vm.md`.

## Commands

- Run all tests in parallel: `make test` (defaults to `raco test -j $(nproc) tests/`).
- Run a subset: `make test TESTS="tests/lexer-test.rkt tests/parser-test.rkt"`.
- Control workers: `make test JOBS=8`.
- Run a program: `racket src/main.rkt examples/hello.agc`; check only: `racket src/main.rkt check file.agc`
- Bytecode VM (`docs/vm.md`): `make vm` builds `dist/agentica-vm` (libgc comes from the `vm/third_party/bdwgc` submodule: `git submodule update --init`); `make vm-test` runs the C tests; `make vm SANITIZE=1` builds with ASan+UBSan; `make vm-fuzz` runs the loader fuzzer; `make vm-gc-stress` runs the C and differential tests on a build that collects often; `make vm-unicode` regenerates `vm/unicode_data.c` from Racket (use Racket CS 9.3, the CI version). Compile with `racket src/main.rkt compile file.agc -o file.agcb`, run with `dist/agentica-vm -- file.agcb`, or do both with `racket src/main.rkt --vm file.agc` (`AGENTICA_VM=path` picks another VM binary). `tests/vm-diff-1-test.rkt` … `vm-diff-4-test.rkt` compare the VM with the evaluator (shared code in `tests/vm-diff-common.rkt`; each shard takes a fixed share of the fixtures so `raco test -j` runs them in parallel).
- Agent evaluation (not part of `make test`): `python3 tests/eval/run.py --help`. Docker is the default; its image is built automatically when missing. Allow provider credentials with repeatable `--pass-env NAME`. Optional Firejail requires `--sandbox firejail --chroot-root PATH`. `--jobs N` runs in parallel.
- Documentation site (`site/`, Hugo extended 0.167): `make site` builds `site/public` (warnings fail the build); `make site-serve` serves it at `http://localhost:1313/agentica/`. Styles are SCSS partials in `site/assets/scss/` (custom properties in `_tokens.scss`), compiled by Dart Sass through Hugo Pipes and minified with the JS and HTML; `make site` needs Dart Sass's `sass` on PATH or in `~/.local/opt/dart-sass` (pinned version and sha256 in `pages.yml`). The user docs live in `site/content` (Getting started, the Language tour in `tour/`, one Library page per builtin module in `library/`), with order and titles in front matter (`title`, `weight`); `docs/grammar.md` is mounted as the language specification (`/reference/`). The programming skill is for agents and is not published. Every `agentica` code block in `site/content` must be a complete program: `tests/site-examples-test.rkt` checks each one and runs it (stdin from an optional `input` block right after it), comparing stdout with the `output` block that follows. `make test` runs it, and `.github/workflows/site-examples.yml` runs it alone on pull requests that change only `site/content` (CI skips those). Fence attributes: `{mode="check"}` only checks (for examples that touch files, processes, the network or other outside state), `{expect="CODE"}` expects that diagnostic, `{file="name.agc"}` is a module that the page's other blocks can import. When the language or a builtin changes, update the matching site page too. The site is built only after a merge: `.github/workflows/pages.yml` runs `make site` on `master` pushes that touch the site or its sources and deploys it to GitHub Pages, so run `make site` locally before merging a site change. Links to the GitHub repo are shown only when `params.repoPublic` is true.
- CI (`.github/workflows/ci.yml`) runs its checks on pull requests, on the self-hosted Linux runner (`docker-runner` label): `make vm vm-test`, `make test` and the example smoke tests, a check that `vm/unicode_data.c` is up to date (skipped when the generator, the table and the Makefile's `vm-unicode` rule match an earlier passing check), plus a `vm-sanitizers` job (the ASan differential and bytecode tests, the fuzz smoke and the GC stress build). A first `changes` job diffs the pull request merge commit against its base (`git diff HEAD^1 HEAD`) and runs `vm-sanitizers` only when the VM, lowering or bytecode files, or CI itself, change (`vm/`, `src/lower.rkt`, `src/bytecode.rkt`, `src/version.rkt`, `tests/vm-diff-*`, `tests/cli-in-process.rkt`, `tests/bytecode-test.rkt`, `tests/fixtures/vm/`, the Makefile, `ci.yml`); otherwise it shows as skipped. If `changes` fails, `vm-sanitizers` still runs. A manual run always runs it. Front-end changes (checker, AST, builtins, `main.rkt`) skip `vm-sanitizers` on purpose; the `test` job still runs the `vm-diff` shards with the real VM for parity. Keep that path list in `ci.yml` in step with new VM files. Pull requests and `master` pushes that change only docs, the site or Markdown skip the whole CI workflow. Compiled Racket files are cached per job (`vm-sanitizers` and `site-examples.yml` fall back to the `test` cache). A `master` push runs no tests, only two jobs that fill caches under the `test` job's keys: `warm-cache` compiles the Racket files and `warm-unicode` runs the unicode check (a separate job, so a stale table fails `master` without losing the compiled-files cache), because a pull request can restore caches saved on its own merge ref or on `master`, never another pull request's; a newer push cancels an older run. Run by hand (Actions → Run workflow): `platforms.yml` runs `make vm vm-test` and the VM differential and bytecode tests on macOS and Windows (MSYS2 UCRT64); `fuzz.yml` fuzzes the sanitizer VM with 5 million mutants and a random seed. Run `platforms.yml` before merging a change to platform code (`vm/main.c`, the Makefile, file or process handling). macOS and Windows are paused until further notice: `platforms.yml` is not run and only Linux is required. Their platform code is kept but untested; Linux code goes under `#ifdef __linux__`. All on Racket CS 9.3.

`make test` wraps `raco test`; a single stage still works directly with `raco test tests/<stage>-test.rkt`.

## Layout

- `src/` is flat, one module per stage: `lexer.rkt` → `parser.rkt` (with `ast.rkt`) → `modules.rkt` (import linking) → `checker.rkt` → `evaluator.rkt`; for the VM, `checker.rkt` → `lower.rkt` → `bytecode.rkt`, run by the C VM in `vm/`. Builtins are described once in `builtins.rkt`; runtime libraries (tasks, files, processes, network, HTTP, JSON, BDD) have their own modules.
- `source.rkt`, `token.rkt`, `diagnostic.rkt` hold shared data (positions/spans, tokens, diagnostics).
- `main.rkt` is a thin CLI driver. Printing and exit codes belong there only.
- `tests/<stage>-test.rkt` holds the focused tests for each stage.
- `.agents/skills/agentica-development/` has stage-by-stage notes. Read it before changing a stage.

## Conventions

- Each stage takes the previous stage's output and returns data or exactly one `diagnostic`. It stops at the first error, never prints, and never lets a Racket exception escape.
- Diagnostic codes are stable and prefixed by stage: `LEX-`, `PARSE-`, `CHECK-`, `RUNTIME-`; the VM compiler stages use `LOWER-` and `BYTECODE-`. Every diagnostic carries a source span.
- Keep to the core grammar (sections 4–6). User enums (generic only through enum declarations) and `case` pattern matching are core; there are no other user generics. File modules with explicit imports/exports are core; the builtin generics `List[T]`, `Map[K, V]`, and `Result[T]` and their builtin modules are core. `try` is builtin error propagation. Planned syntax stays in `docs/future.md` until its phase lands. No placeholder files or nodes for later phases.
- Use Racket's built-in test support (`rackunit`) as the test framework. Independent integration counterparts may use Node.js, Python, or curl; use standard libraries and add no third-party libraries or test frameworks.
- Network and process tests must stay hermetic: localhost, dynamically assigned ports (port 0), no external services, and cleanup of processes and resources. TCP/HTTP interoperability tests must use an independent protocol implementation as the counterpart, rather than relying only on the Agentica client and server testing each other. Put fixtures in `tests/fixtures/`. These tests are required in CI: install their chosen tools and fail if they are missing. Local runs may explicitly report a skip when a required tool is unavailable. Racket-only tests may complement this coverage; they are not required as the base layer.
- Tests assert the diagnostic code (and the span when it matters), not message text.
- When a phase item is finished, tick it in the roadmap and update the development skill.
- When the language changes, update `docs/grammar.md` and the programming skill together: the core language is in `.agents/skills/agentica-programming/SKILL.md`, and each library area has its own file in `references/` (builtins, modules, JSON, files, processes, tasks, network, BDD, diagnostics, examples). The skill is self-contained and does not read the grammar. Keep `SKILL.md` near 5,000 tokens; put new library detail in the matching reference and its row in the "When to read a reference" table.

## Working style

- Think briefly. If something is unclear, try it, see what fails, then fix it.
- Use simple words.
